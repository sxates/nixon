# 0051 — 1.14 feedback batch: mid-recording mode toggle + stop-time processing handoff

- **Status:** Implemented (pending owner smoke)
- **Owner agent(s):** audio-engineer (WS1) + frontend-engineer (WS2–WS4) + rust-core-engineer (WS2 reconciliation)
- **Roadmap phase:** Feedback batch (1.14)

## Context / Problem

Three owner-reported items from a real 1.14 meeting. Two of them share one call: the owner
changed "Label speakers live while recording" in Settings, accidentally clicked the recording's
**Live** chip (switching it to **Deferred**), then switched it back to **Live**.

**1. Live transcription appeared to stop, and the *existing* transcript's layout started
changing.** Root-caused, not speculative:

`SttStage::sync()` (`frontend/src-tauri/src/audio/stt_stage.rs:64`) **drops** the
`ContinuousVadProcessor` on go-deferred and constructs a **brand-new one** on go-live. A fresh
VAD restarts its clock at zero, so every post-resume segment arrives with
`start_timestamp_ms ≈ 0`. `TranscriptContext` re-sorts the entire list by `chunk_start_time` on
every batch (`frontend/src/contexts/TranscriptContext.tsx:329`), so the resumed lines were
**inserted at the top**, interleaved among the meeting's opening lines. From where the owner was
watching (the bottom), that reads exactly as "transcription stopped" *plus* "the transcript I
already had is rearranging itself."

Two further consequences of the same desync:
- `vad_fed_ms` — the channel-dominance clock (`pipeline.rs:1087`) — keeps its pre-defer value, so
  `dominant_channel_for_span` looks up a span the re-based VAD never produces. Mic-vs-system
  attribution goes wrong for the whole resumed tail, which is the input diarization builds on.
- Detach deliberately drops the un-flushed VAD tail (`stt_stage.rs:78`), justified by "a deferred
  meeting gets a full retranscription later anyway."

The **"Label speakers live while recording" toggle was not implicated.**
`live_diarization_enabled` is read once at recording start (`recording_commands.rs:126`) and
`diarization/settings.rs::save_settings` has no effect on a running session. It was inert — it
misled the owner into suspecting it, but it broke nothing.

**2. At meeting end, nothing ran** — no speaker identification, no summary — and the saved
transcript was short. The stop path *should* have reached `stopAction → 'process-now'`
(`processing-mode.ts:117`), which dispatches a window event driving retranscribe → diarize →
summarize. That branch also **suppresses both normal fallbacks**:
`shouldAutoDiarizeAtStop('process-now')` is `false`, and `autoSummarySkipReason` returns
`'deferred-processing'` and skips **silently** by design (`auto-summary.ts:73,105`). So a single
missed `window.dispatchEvent` produces precisely the observed outcome: nothing runs, and nothing
says so.

Worse, the resulting state is **permanent**. `list_deferred_candidates`
(`database/repositories/meeting/query.rs:56`) lists only `processing_mode='defer'` **or**
sparse-transcript meetings. A meeting stranded at `processing_mode='live'` with a partial-but-not-
sparse transcript matches neither arm, so the backlog can never pick it up — on any launch, on any
AC connection, ever. (No log evidence survives: `~/Library/Logs/ai.vinyl.app/Vinyl.log` is stale
from 2026-08-04, and frontend console output is not persisted.)

**3. The Zoom mute indicator obscures the transcript.** `ZoomMuteIndicator` (specs/0049) raises a
`duration: Infinity` sonner toast that parks over the bottom of the transcript. The owner does not
want a muted-status indicator at all.

## Goals

- A mid-recording Live↔Deferred toggle produces a **continuous, monotonically increasing**
  transcript timeline aligned to the saved audio, in both directions and repeatedly.
- Stop-time processing is **durable and self-healing**: a failed handoff is retried on a later
  launch or AC connection, never stranded, and never silent.
- The meeting already damaged by this bug is repaired automatically.
- Settings that cannot affect a running recording say so instead of implying they took effect.
- No muted-status toast over the transcript.

## Non-goals

- Locking down the Live/Deferred chip or the Recording settings panel during a recording. The
  owner explicitly chose "keep them editable, tell me when a change only applies next time."
- Any change to diarization clustering, the speaker-count seed (0050), or the mute **gate** itself
  (0049) — only its toast is removed.
- Persisting frontend console logs. Worth doing, but it is its own change.

## Approach

Fix the timebase rather than forbid the toggle, and make the stop-time handoff durable rather than
adding a retry around a fire-and-forget event.

For the timeline, the anchor must be a clock that (a) advances **across** the deferred span and
(b) is aligned to what actually landed in the WAV — otherwise transcript timestamps drift from
audio playback and from the later retranscription merge. The pipeline already feeds every mixed
window to the recorder (`pipeline.rs` STEP 4) *outside* the STT gate, so a sample-derived counter
over those windows is exactly that clock. Wall-clock (`get_recording_duration()`) is **not** used:
it is `Instant::elapsed()` and includes pause time (`recording_state.rs:399`), so it would drift
from the WAV on any paused recording.

For the handoff, the `'live'` marker is inverted into a durable `'defer'` marker written *before*
the pipeline is kicked off. This reuses machinery that already exists — the backlog's own listing
query and its step-4 clear — instead of adding a new pending state, a schema column, or a query
arm, and it makes "the handoff never landed" indistinguishable from "the meeting was deferred,"
which is the case the system already recovers from correctly.

## Design

### WS1 — Session-continuous VAD timebase (audio-engineer)

**`audio/pipeline.rs`** — replace `vad_fed_ms` with `recorded_ms`: the same accumulator, but
advanced for **every** mixed window processed, not only those fed to the VAD. This is the
session's audio clock; it keeps counting through a deferred span because the recorder keeps
receiving windows through it. `record_channel_window` reads `recorded_ms` for its span bounds, so
channel history and VAD segments share one base as they do today.

**`audio/stt_stage.rs`** — `SttStage` gains `offset_ms: f64`.

- `sync(&mut self, recorded_ms: f64) -> SyncOutcome` where
  `SyncOutcome = Attached | Detached | Unchanged`. On attach it sets `offset_ms = recorded_ms`.
- `process()` and `flush()` shift each returned segment's `start_timestamp_ms` /
  `end_timestamp_ms` by `offset_ms` before handing it back, so the segment-dispatch loop in
  `pipeline.rs` is untouched.
- On `Detached`, **flush the VAD before dropping it** and dispatch the resulting tail. The
  existing "drop the tail, we'll retranscribe anyway" rationale does not survive WS2, which makes
  retranscription conditional rather than guaranteed.
- On `Attached`, the pipeline clears `channel_windows` (their spans predate the gap and can only
  mis-resolve).

This also corrects the **started-deferred → go live** path, which has the same bug today (offset
should be the go-live position, is currently 0). It is invisible only because those meetings are
always fully retranscribed at stop — the same one-line fix covers it.

### WS2 — Durable processing marker + verified handoff (frontend-engineer, rust-core-engineer)

**Marker inversion** (`frontend/src/hooks/useRecordingStop.ts`). For `stopAction === 'process-now'`,
write `processing_mode='defer'` **first**, then start the pipeline. The backlog's existing step 4
(`useDeferredBacklog.ts:350`) clears it on success. Consequences, all from existing code paths:

- a handoff that never lands leaves a `'defer'` meeting → `list_deferred_candidates` picks it up
  on the next launch or AC connection;
- `autoSummarySkipReason` sees `'defer'` → `'deferred'` → the user gets the "use Process now"
  toast instead of a silent `'deferred-processing'` skip;
- retention still exempts it (`audio/retention.rs:84`).

The `'deferred'` toast copy in `auto-summary.ts` currently says "recorded in low-power mode,"
which no longer covers this case; it is reworded to be mode-agnostic.

**Acknowledged handoff.** `useRecordingStop` calls `useBacklog().enqueueMeeting` through the
existing `DeferredBacklogProvider` context and awaits a result, replacing
`window.dispatchEvent('process-deferred-meeting-now')`. `enqueueMeeting` currently returns `void`
and **silently early-returns** when `folder_path` is missing (`useDeferredBacklog.ts:461`) — a live
silent-drop path; it returns a discriminated result instead. On any failure the stop path runs the
normal auto-diarize + auto-summary it would otherwise have run, and toasts. The window-event
listener stays (the per-meeting "Process now" button and `TranscriptButtonGroup` use it).

**Startup reconciliation** — new `frontend/src-tauri/src/audio/processing_reconcile.rs`, called
from the existing startup path. On app start, rewrite any `processing_mode='live'` row to
`'defer'`. A lingering `'live'` can only mean processing never completed, and no recording can be
in progress at startup. Best-effort: a failure logs and leaves the row alone; the next launch
retries.

This is deliberately a **startup sweep, not a widened `list_deferred_candidates`**: the mode chip
sets `'live'` on a meeting *while it is still recording*, so an `OR processing_mode = 'live'` arm
would let the backlog — which by design has no recording-state dependency
(`useDeferredBacklog.ts:5`) — start retranscribing a meeting underneath an active recording.

This is what repairs the owner's existing meeting on the next launch.

### WS3 — "Applies to your next recording" notices (frontend-engineer)

Three settings are read once at recording start and are inert mid-session:

| Setting (RecordingSettings.tsx) | Backing pref |
|---|---|
| Transcribe in real time during recording (`:517`) | `live_transcription_enabled` |
| Low Power Mode on battery (`:538`) | `low_power_on_battery` |
| Label speakers live while recording (`:627`) | `live_diarization_enabled` |

Everything else in the panel stays honest mid-recording and gets **no** notice: **Speaker
diarization**, **Expected number of speakers**, and the voiceprint toggles all still feed the
post-meeting pass; **Summarize automatically** is read at stop. A notice on those would be wrong
in the other direction.

The save still goes through; a toast follows: *"Saved — applies to your next recording."* For
**Transcribe in real time** the copy points at what does work now: *"Use the Live/Deferred button
on the recording to change this meeting."*

The set of start-time-only settings lives as one exported map (setting key → notice copy) in a
new `frontend/src/lib/recording-settings-notices.ts`, not as flags through the JSX —
`RecordingSettings.tsx` is 758 lines against the 800-line ratchet (specs/0042). The
active-recording signal is `activeRecordingMeetingId` from `SidebarProvider`, which survives
navigating away from `/record` (the user is in Settings when this fires).

### WS4 — Remove the mute toast (frontend-engineer)

Delete `frontend/src/components/ZoomMuteIndicator.tsx` and its import + mount
(`frontend/src/app/layout.tsx:31,278`). The 0049 gate is untouched: the mic still pauses while
muted and `zoom-mute-changed` still fires.

### Data model

No schema change. Reuses `meetings.processing_mode` (`'live' | 'defer' | NULL`) with `'defer'`
carrying "needs processing" for both the low-power and the mid-meeting-override cases.

### Tauri IPC

No new commands or events. WS2's reconciliation runs in-process at startup; WS1 is entirely
internal to the audio pipeline.

## Risks / open questions

- **WS1 touches the machinery 0046/0047 tuned.** The change moves timestamps toward correctness,
  so it should not perturb owner-boundary splitting or the bleed guard — but the DER gate
  (`tests/diarization_tuning.rs`) runs on pre-recorded audio, not live toggling, and will not
  catch a regression here in either direction. The live → defer → live smoke below is the only
  real check.
- ~~**Pause interaction.**~~ **Resolved during planning:** `RecordingState::send_audio_chunk`
  discards chunks outright while paused (`recording_state.rs:279`), so the pipeline receives no
  windows and `recorded_ms` stalls in lockstep with the WAV. No pause gate is needed on the
  counter.
- **Double-drain.** Marking `'defer'` before the forced enqueue means the mount-time backlog
  refresh could also see the meeting. `drain()` early-returns when a drain is running
  (`useDeferredBacklog.ts:365`) and `enqueueItems` dedupes by id, so this should be inert —
  verify with a test rather than by inspection.
- **`'defer'` semantics widen.** `'defer'` now means "needs processing" generally, not "recorded
  in low-power mode." Any copy or logic keying off it as a low-power signal needs an audit pass;
  `auto-summary.ts` is the known one.

## Follow-ups (parked, non-blocking)

Raised by the final whole-branch review, judged not to block the merge:

- `audio/processing_reconcile.rs` — `spawn_blocking` wraps `get_default_recordings_folder`, which
  does no I/O; the actual blocking work (`scan_interrupted_recordings`' `read_dir` + a
  `metadata.json` read per folder) runs inline on the async task. The comment claims the opposite.
  Move the scan inside `spawn_blocking`. Impact: one Tokio worker stalled at startup in proportion
  to library size — noticeable only on a large library or a networked volume.
- `tests/pipeline_integration.rs` — the channel test's third assertion is annotated
  "(channel_windows must be cleared on attach)", but removing that `clear()` leaves it green. The
  assertion is a valid no-mic-bleed check; the parenthetical credits a mechanism it doesn't
  exercise. The `clear()` is genuinely redundant (post-gap segments span `[T_attach, ∞)`, pre-gap
  windows end at `T_detach ≤ T_attach`, and `dominant_channel_for_span` requires strict positive
  overlap) — keep it as a guard against future re-basing, but fix the comment.
- `app/meeting-details/page.tsx` — `backlogItems` joins a dependency list whose "check once" guard
  (`hasCheckedAutoGen`) only closes after two awaits, so a backlog dispatch landing in that window
  can re-run the gate. Pre-existing (`meetingDetails` and `isTranscriptsLoading` already do this);
  this widens it. A `useRef` latch instead of the `useState` guard would close it.
- Both the startup sweep and `api_list_interrupted_recordings` resolve the recordings root via
  `get_default_recordings_folder()`, ignoring a user's configured `save_folder`. Pre-existing — a
  user with a custom folder gets no resume prompt today either — and the sweep is consistent with
  it, so nothing new diverges. Worth fixing on its own terms.
