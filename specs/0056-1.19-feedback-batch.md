## Context / Problem

Seven owner-reported items from dogfooding v1.19.0 (2026-09-01). The active provider is
**Ollama / `gemma4:26b`** (confirmed in the dev DB's `action_item_extractions` ledger and the
0054 notes).

1. Use the Google photos already fetched for calendar attendees for **People** avatars.
2. People detail page → **Voice Samples tab does not scroll**.
3. **Summarize** on a person with many recent meetings returned *"Nothing notable to
   summarize from recent meetings"*.
4. The **prep drawer** on the record screen has no side padding; the owner wants a single
   right-hand rail with **Notes / Prep tabs** instead of a separate drawer.
5. **Ask AI** could not answer *"in what meeting did Arno mention that he talked to Frank?"*
   although the answer was in the transcript of a meeting it examined.
6. Ask AI is **delayed behind background work** (action-item extraction), then **times out**;
   later retries also failed — "I can't get any answers from Ask AI right now".
7. **Action-item extraction runs for a while, then fails.**

### Evidence gathered before design

**Items 3, 6 and 7 share one root cause, reproduced on the owner's own model.** `gemma4:26b`
advertises the `thinking` capability (`/api/show` → `capabilities: [completion, vision, tools,
thinking]`), and Ollama's OpenAI-compatible endpoint **thinks by default**. The reasoning is
returned in a separate `message.reasoning` field that Vinyl never reads, and every reasoning
token counts against `max_tokens` — which Vinyl caps at 4096 for Ollama (specs/0052).

Replaying Vinyl's exact person-roll-up reduce prompt (6 real summaries from the dev DB,
1,561 prompt tokens) against `gemma4:26b` on 2026-09-01:

| Request shape | Wall clock | `completion_tokens` | `finish_reason` | `content` |
|---|---:|---:|---|---|
| **As shipped** (thinking on) | 59.4 s | 4,096 (all reasoning: 14,395 chars) | `length` | **empty** |
| `reasoning_effort: "none"` | 3.4 s | 156 | `stop` | a correct 621-char roll-up |

An empty `content` is exactly what `person-details/page.tsx:513` renders as *"Nothing notable
to summarize"* (the frontend-only empty-markdown branch; the backend's own "nothing to roll up"
short-circuit is a different, non-empty string). The same shape explains the rest:

- **Extraction (7):** replayed with the real extraction prompt + `response_format:
  json_object` on a short dev summary: **15.4 s with thinking (3,331 chars of reasoning)
  vs 1.6 s without**, same JSON either way. On the owner's real summaries (several times
  longer, plus an ALREADY TRACKED list) the reasoning scales the way the roll-up's did — once it
  reaches the cap, `content` is empty, the strict parse fails ("no JSON array opening
  bracket"), the one retry at `temperature 0.0` is byte-identical, and the run fails after
  minutes of GPU time — "runs for a while, then fails". A failed run leaves **no DB trace** by
  design, and the only failure text the user can see comes from the LLM-activity popover.
- **Ask AI (6):** every map call over up to 10 meetings, plus the reduce, thinks for up to a
  minute; a background extraction thinking at the same time queues *ahead* of it inside Ollama
  (`OLLAMA_NUM_PARALLEL` defaults to 1), and `reqwest`'s 300 s timeout starts at send — so the
  queue wait is billed to the Ask AI call. `processor.rs` then retries a timeout twice (3 × 300 s
  per map call). From the UI this is indistinguishable from a hang.

Two switches were tested: `think: false` is **ignored** by the `/v1/chat/completions` endpoint
(reasoning still returned); `reasoning_effort: "none"` **works** (Ollama 0.32.14 here; the owner's
work machine runs 0.32.12) and is **harmless on non-thinking models** (`gemma3:27b`: identical
answer, no error).

**Item 6 also has a structural half.** There is **no app-level LLM scheduling at all**: summaries,
auto-extraction, prep passes, person roll-ups and Ask AI all call `generate_summary` freely.
`llm_activity` is observability only, `TaskKind::AskAI` is never constructed, and the only locks
are per-meeting dedup (`action_items::IN_FLIGHT`) and the prep pass single-flight. With one local
model, "parallel" is not available — but **priority** is: an interactive request must not wait
behind background work.

**Item 5 is a separate, certain defect in retrieval** (`aggregation/gather.rs:113-135`). The doc
body is the summary whenever one exists, and the transcript excerpt is attached **only when the
meeting's single best bm25 hit came from the transcript**. bm25 scores are not comparable across
the three FTS tables (documented in `search.rs`), and a short dense summary usually out-ranks one
transcript segment on generic terms ("meeting", "mention"). So the meeting was gathered, the
model saw the summary, the summary didn't mention Arno↔Frank, and the transcript — which did —
never entered the context. `tests/aggregation_engine.rs:428-433` asserts this as intended. Even
when the excerpt is attached it is speaker-less (`get_transcript_excerpt` selects only
`t.transcript`), so "*who* said X" is unanswerable by construction.

**Item 1:** `attendee_photos` (specs/0038 WS3) already caches same-org directory photos as local
`data:` URIs (220 rows in the dev DB) and the meeting roster already joins it. The People list
and person page never do — they render initials only. The photo pass only "wants" emails that
appear in the cached calendar window, so a person who isn't a recent attendee has no photo even
though the directory read that could supply it already runs.

**Item 2:** `VoiceprintSamplesList.tsx:221` wraps the list in a Radix `ScrollArea` with
`max-h-[52vh]` and no definite height. Radix's viewport is `h-full`, which resolves to `auto`
against an auto-height parent, so the viewport never overflows itself and the scrollbar is
never enabled; the root's `overflow-hidden` then **clips** at 52vh. The two sibling tabs are
plain blocks that scroll with the page container.

**Item 4:** `PrepDrawer.tsx:74` mounts `PrepPanel` in a `min-h-0 flex-1 overflow-y-auto` container
with no gutter; `PrepPanel` assumes its ancestor supplies one (in meeting-details it is the
`px-6 sm:px-8` reading column). Meeting-details already has a Notes/Prep tab pair rendering the
very same two components (`useMeetingTabs`, `MeetingTabPanels`), so the rail can copy it.

## Goals

- W1 — Local thinking models produce **answers, not empty replies**: no reasoning on Ollama,
  an empty reply is an error (never a silent blank), and inline `<think>` blocks never reach the
  aggregation UI.
- W2 — **Interactive LLM work (Ask AI, person roll-up, manual "Scan again") is never queued
  behind background work** on a local model; background jobs are serialized among themselves
  and yield to interactive requests.
- W3 — Ask AI sees **transcript evidence with speaker names** whenever the question hit the
  transcript, regardless of which source ranked best.
- W4 — The record screen has **one right-hand rail with Notes / Prep tabs**; prep content has
  the same gutter as everything else on that screen.
- W5 — Voice Samples tab scrolls like its siblings; the dialog variant keeps its bounded height.
- W6 — People directory and person page show the **cached Google directory photo** when one
  exists, initials otherwise; people who aren't recent attendees get their photo on the next
  photo pass.
- W7 — Diagnostics tell the truth: the timeout message says 300 s, extraction failures log
  provider + model, the BuiltInAI sidecar cannot hand one caller another caller's reply.

## Non-goals

- **No Ollama `think` capability probing.** `reasoning_effort: "none"` is accepted by non-thinking
  models, so it is sent to every Ollama request unconditionally. Not sent to CustomOpenAI (an
  unknown server may reject unknown fields) or cloud providers.
- **No user-facing "reasoning on/off" setting.** Every Vinyl prompt is extraction, summarization
  or grounded QA with a tight output budget; there is no call site that benefits from reasoning.
  Revisit if a future feature wants it.
- **No FTS tokenizer change** (stemming: "talked" vs "talk"). It requires rebuilding the FTS
  tables; backlog.
- **No speaker-name FTS index.** W3 attaches speaker-labelled transcript windows; matching a
  person's *name* as a query term stays a backlog item.
- **No true parallelism on a local model.** W2 is priority + serialization, not concurrency;
  `OLLAMA_NUM_PARALLEL=1` remains correct.
- **No new Google scope or egress path.** W6 reuses the directory read that already runs and the
  `attendee_photos` cache; Disconnect still purges it.
- The pinned agenda strip above the notepad (`RecordAgendaPanel`, specs/0036) is unchanged — the
  owner asked to merge the *drawer*, not the strip.

## Approach

Fix the shared root cause first (W1) because it is the cheapest change with the largest effect,
and it is proven against the owner's model. Then add scheduling (W2) so the remaining latency is
ordered by what the user is waiting for. W3 fixes retrieval independently. W4–W6 are frontend /
query changes with no LLM involvement. W7 is small correctness debt found while mapping.

## Design

### W1 · Thinking models on Ollama

`llm_client::build_chat_request_body` adds `reasoning_effort: "none"` to the request body for
`LLMProvider::Ollama` only (`ChatRequest` gains an `Option<String>` field, skipped when `None`).
Tests: Ollama body carries it; OpenAI/Groq/OpenRouter/CustomOpenAI/Claude bodies do not.

`generate_summary_with_options` treats an **empty trimmed `content`** as
`Err("The model returned an empty reply …")` for every provider. Previously an empty string
flowed to callers as success: roll-up → blank card; Ask AI → blank answer; extraction → a parse
failure with a misleading "no JSON array" cause. The error names the likely cause (output budget
spent on reasoning) so a user on a non-Ollama thinking model gets an actionable message.

`ChatResponse.message.content` becomes `Option<String>` (Ollama emits `null` content when a
model returns only tool calls or reasoning) — `None` is the same empty-reply error, not a
deserialization failure.

Aggregation consumers (`rollup.rs`, `aggregation/commands.rs`, `prep_jobs.rs`) run the reduce
output through `clean_llm_markdown_output` like the summary path does, so an inline
`<think>…</think>` block or a wrapping code fence from a model that emits them in-band never
reaches `AnswerMarkdown`.

### W2 · LLM scheduling: interactive preempts background

New module `summary/llm_gate.rs`, entered from `generate_summary_with_options` — the single
choke point — for the **local providers only** (`Ollama`, `BuiltInAI`). Cloud providers are
parallel and remote; they bypass the gate.

- `Priority::{Interactive, Background}`; the current priority is a `tokio::task_local!` set by
  `llm_gate::with_priority(Priority::Interactive, fut)` at the interactive entry points:
  `api_ask_ai_run`'s spawned task, `api_person_rollup`, `api_extract_action_items` ("Scan
  again"), `api_regenerate_prep_brief`. Everything else defaults to `Background` (summaries,
  auto-extraction, prep passes, outline, note enhancement).
- **Background** calls acquire a global `Semaphore(1)` permit **and** wait until no interactive
  call is in flight before sending. This serializes background jobs among themselves — they
  were piling onto one model and each paying the others' queue time against its own timeout.
- **Preemption (Ollama only):** a background HTTP request in flight races against an
  "interactive requested" signal; when it fires the request future is **dropped** (Ollama aborts
  generation when the client disconnects), the permit is released, and the call is **re-issued
  from scratch** after interactive work drains. A bounded number of preemptions per call
  (`MAX_PREEMPTIONS = 3`) before the call proceeds without yielding, so background work cannot be
  starved forever by a stream of questions.
- **BuiltInAI:** no preemption — the sidecar has no per-request cancel short of killing the
  process. Background calls wait for interactive ones to finish before *starting*; the sidecar
  itself gets the W7 request lock so replies cannot cross.
- **Interactive** calls run outside the semaphore (two questions may queue behind each other
  inside Ollama — acceptable) and register/unregister on the interactive counter.
- The gate is process-global (`OnceLock`), infallible, and never holds a lock across an await
  other than the semaphore permit itself. Unit tests drive it with a fake "request" future:
  background waits for interactive; an interactive arrival preempts an in-flight background
  future exactly once and the call re-runs; preemption count is bounded.

`engine::map_llm_error` stops inferring cancellation from the substring "cancelled" — only the
run's own `CancellationToken` decides — so a real failure can no longer be swallowed by the Ask
page's silent-cancel branch. `api_ask_ai_run` registers itself in the LLM-activity registry as
`TaskKind::AskAI / Origin::Foreground` so it is visible to diagnostics.

### W3 · Transcript evidence for Ask AI

`RankedMeeting` gains `transcript_hit_ids: Vec<String>` — the top-`K` (K = 3) transcript segments
for the meeting by bm25, computed with `ROW_NUMBER() OVER (PARTITION BY meeting_id ORDER BY rank)`
inside the existing rank CTE, **independent of which source won overall**. The rank SQL moves to
a new `database/repositories/search_rank.rs` (search.rs is allowlisted at 984 and may only shrink).

`gather.rs` attaches an excerpt whenever `transcript_hit_ids` is non-empty and the body is not
already the transcript. The excerpt is built by a new
`TranscriptsRepository::get_transcript_excerpts_with_speakers(meeting_id, &ids, window)` in a new
`transcript_excerpt.rs` (transcript.rs is allowlisted): the ±15-segment windows around each hit
are merged when they overlap, ordered by recording time, and each line is prefixed with the
resolved speaker display name (`speakers` join, same as `get_transcript_segments_with_speakers`)
when one exists. Windows are labelled `[…]` between gaps.

The existing integration tests that assert "no excerpt when the summary is the best hit" are
inverted to assert the new policy, with a new case: evidence only in the transcript, summary
present and ranked higher → the excerpt is present, carries the speaker name, and the map prompt
contains it.

### W4 · Record-screen rail with Notes / Prep tabs

`app/record/page.tsx`: the right column becomes `RecordRail` (new
`components/Record/RecordRail.tsx`): a WAI-ARIA tablist (copying `MeetingTabsBar`'s underline
styling and roving tabindex) with **Notes** and **Prep** tabs, then the panels.

- Notes panel = existing `RecordAgendaPanel` strip + `NotepadPanel` (unchanged, `variant="panel"`).
  It stays **mounted** when Prep is active (hidden with `hidden`), so the notepad's debounced
  autosave and unmount-flush behaviour (`NotepadPanel.test.tsx`) are untouched.
- Prep panel = `PrepPanel` inside a `min-h-0 flex-1 overflow-y-auto px-5 py-4` scroller — the
  `px-5` gutter is the record-screen convention (`TranscriptPanel`, `NotepadPanel`,
  `RecordAgendaPanel`). **Lazily mounted on first activation** (as the drawer and meeting-details
  do, because `api_get_prep` kicks off brief generation when absent) and kept mounted after.
- The Prep tab exists whenever there is an `activeRecordingMeetingId`; its label carries the
  `openItemCount` badge from `usePrepAvailability`. Before a meeting row exists only Notes shows.
- `PrepDrawer.tsx` and the header `prep` button/prop are deleted.

Tests (`RecordRail.test.tsx`): Notes is default; `PrepPanel` is not mounted until the Prep tab is
clicked; switching back leaves the notepad mounted; the badge renders the count; arrow keys move
between tabs.

### W5 · Voice Samples scroll

`VoiceprintSamplesList` gains `bounded?: boolean`. The dialog passes `bounded` and gets
`max-h-[52vh] overflow-y-auto` (native scroll, which is what its sibling `ModelSettingsModal`
usage already relies on). The person page passes nothing and the list flows in the page's own
scroll container like the other two tabs. The Radix `ScrollArea` is removed here.

### W6 · People photos

`Person` gains `photo_data_uri: Option<String>` (`#[sqlx(default)]`, serialized `photoDataUri`),
populated by `LEFT JOIN attendee_photos ap ON ap.email = LOWER(TRIM(p.email))` in
`PeopleRepository::{list, list_ranked, get}`. New shared `components/People/PersonAvatar.tsx`
renders the photo (`<img>` with `onError` → initials, same pattern as `AvatarStack`) and is used
by the directory row and the person page header.

`fetch_attendee_photos` (extracted from the allowlisted `sync.rs` into a new
`calendar/google/photos.rs` as a no-behaviour-change move first) widens the wanted set to
**cached attendees ∪ people with an email**, so a person who isn't in the calendar window still
gets a photo on the next pass. Same TTL, same directory read, same purge on Disconnect.

### W7 · Diagnostics and sidecar correctness

- `llm_client.rs`: the no-cancellation-token branch says "300 seconds" (it said 60).
- `extractor.rs` unparseable-reply warn line carries provider + model (the 0054 spec promised
  this; the shipped line omitted them).
- `sidecar.rs::send_request`: one `request_lock` held across write **and** read so two callers
  cannot interleave on the single stdin/stdout pipe; the timeout wraps only the write+read, not
  the lock wait, so a queued caller is not billed for the one ahead of it.

## Acceptance criteria

- Ollama request bodies carry `"reasoning_effort":"none"`; no other provider's body does.
- The replayed roll-up prompt (spec table above) returns a non-empty roll-up through the real
  request builder.
- `generate_summary_with_options` returns `Err` for `content: ""` and `content: null`.
- A background call started before an interactive one is preempted and re-issued; an interactive
  call never waits on the background semaphore (unit tests with fake futures).
- A question whose only evidence is in the transcript of a summarized meeting yields a doc whose
  `full_text()` contains the speaker-labelled transcript line (integration test).
- Voice Samples tab: list longer than the viewport scrolls with the page; dialog still bounded.
- People row and person header render `<img>` when `photoDataUri` is present, initials otherwise.
- Record screen: Notes/Prep tabs; PrepPanel content has `px-5`; PrepPanel is not mounted until
  Prep is clicked; NotepadPanel stays mounted across switches.
- DoD gate green; ratchet: `search.rs`, `transcript.rs`, `sync.rs`, `extractor.rs`, `prompts.rs`
  do not grow.

## Risks / open questions

- `reasoning_effort` on an **old Ollama** (< 0.11) is an unknown field: Ollama's OpenAI layer
  ignores unknown fields rather than rejecting them, but this was only verified on 0.32.x.
- Preemption assumes Ollama stops generating when the HTTP connection drops. Verified behaviour
  for Ollama's server; if a proxy sits in front of it the wasted generation is bounded by
  `max_tokens` anyway.
- The transcript excerpt makes Ask AI prompts larger (≤ 3 windows × 31 segments per meeting);
  the engine's existing budget check falls back to map-reduce, so this trades tokens for recall.
- W4 has **no human smoke** until the owner records a meeting (same caveat as 0054 W4).
