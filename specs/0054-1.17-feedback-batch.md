   with *"Could not save template choice — the template will be used for now, but may not
   persist."*
3. **Meeting volume has reached hundreds over a couple of months.** The owner wants search
   and a way to browse back in time that is not a single long list.
4. **Prep content is unreachable during a live recording** — only the typed agenda is pinned.
5. **Some cancelled meetings never leave the agenda.** Owner reports these are *recurring*
   meetings and that they are stuck **permanently** (not cleared by a restart).

## Approach

Five independent work-streams in one branch, ordered so the two certain root causes (W2, W5)
land first and the uncertain one (W1) is gated behind a reproduction.

W1 fixes a **contract mismatch** rather than adding another sampling knob: the request asks
for `response_format: {"type":"json_object"}` while the prompt and parser demand a top-level
array. Aligning the contract to an object is strictly better than dropping json mode, because
it keeps the grammar constraint working *for* us on providers that honour it.

W5 fixes **cache poisoning at the source** plus a one-time purge. The alternative — teaching
the delete path to also try series-prefix deletes — treats the symptom and leaves the phantom
rows showing phantom meetings until they age out.

## Design

### W1 · Action-item extraction on Ollama

**Mechanism.** `extractor::extract_candidates` passes
`GenerationOptions::deterministic_json()`. `llm_client.rs:86` turns that into
`response_format: {"type":"json_object"}` for *all* OpenAI-compatible providers, Ollama
included. Ollama enforces json mode as a decoding constraint: the model must emit a top-level
JSON **object**. But `build_system_prompt` asks for a top-level **array**, `RETRY_REMINDER`
(`extractor.rs:249`) insists on *"starting with `[` and ending with `]`"*, and
`parse_candidates` (`extractor.rs:393`) slices first `[` … last `]` then runs a strict
`serde_json::from_str::<Vec<ActionItemCandidate>>`. The slice rescues `{"action_items":[…]}`
by coincidence; it produces invalid JSON for an object whose array is nested deeper, and
fails outright for an object with no array. Both attempts fail the same way, so the retry
cannot help, and `run_extraction` surfaces *"Action-item extraction failed"*.

Cloud providers treat `json_object` as a soft hint and usually return the array anyway, which
is why this never showed up outside the local path.

**Diagnostics first (ships before the fix).** Extend the existing content-free failure log in
`extract_with_llm` (`extractor.rs:445`) and the LLM-activity failure row with: provider,
model, reply length in chars, the first non-whitespace character of the reply, and the parse
error. No reply content — privacy (this is the same class as the `service.rs:692` title leak
noted in 0053).

**Fix.** Object-wrapped contract:

- `build_system_prompt` requests `{"action_items": [ … ]}`.
- `RETRY_REMINDER` restates the object form.
- `parse_candidates` gains a two-shape parse: try `{"action_items": [...]}` first, fall back
  to a bare `[...]`. Both keep the existing fence-strip and bracket-slice defenses. The
  fallback is what keeps already-working cloud providers working.

**REPRODUCED (2026-08-25), then fixed.** The gate the spec set was met before any
code changed. Replaying the exact request `build_chat_request_body` produces, with the
real prompts, against `gemma4:26b` on the owner's own Ollama:

| Arm | Reply | `parse_candidates` |
|---|---|---|
| **A** — `response_format: json_object` (shipped) | `{"description": "Send the deck", "assignee": "me", "due": "Friday"}` | **FAILED** — no `[` |
| **B** — no `response_format` (control) | `[{…},{…},{…}]` | **OK, 3 items** |

`completion_tokens` was **31** against the 4096 cap with `finish_reason: "stop"`, so the
spec's truncation check is settled: this is the reply's SHAPE, not its length.

Two things were worse than predicted:

- The model did not merely wrap the array — it **collapsed three action items into one**,
  because a top-level object can hold exactly one item's three keys. Even a parser that
  accepted the shape would have silently lost data.
- Extraction runs at `temperature: 0.0`, so **the retry returns byte-identical output**.
  The one-retry design cannot rescue this failure mode, and never could.

**Fix shipped:** the prompt now asks for `{"action_items": [...]}` — the shape
`json_object` can actually express. **No parser change was needed**: the existing
bracket-slice already recovers the array, and `grammar.rs` already had a passing test for
that shape. A bare array still parses, so hosted providers (which treat json mode as a
hint) are unaffected. Verified end-to-end with the *shipped* prompt string read out of
`extractor.rs`: 3 items, correctly assigned.

### ⚠ Separate environment finding — likely ALSO implicated

While reproducing the above, the first two attempts hung for 15 minutes and returned
nothing. Cause: **two `ollama serve` processes are both bound to port 11434** on the
owner's machine —

```
ollama  1672 ... TCP *:11434 (LISTEN)          # /usr/local/bin/ollama, up since Jul 7
ollama 30031 ... TCP 127.0.0.1:11434 (LISTEN)  # Ollama.app, started Aug 18
```

macOS resolves `localhost` to `::1` first, so requests land on the **stale July process**,
which never loads a model. Measured, same model and prompt: `http://127.0.0.1:11434`
answers in **7 s**; `http://localhost:11434` **never answers**.

Vinyl hardcodes `http://localhost:11434` (`llm_client.rs`, `ollama/*.rs`), so on this
machine every Ollama request hangs until `REQUEST_TIMEOUT_DURATION` (300 s) and then
reports a generic failure. **That is an equally good explanation for the reported
"extraction failed", and for 0053's inability to reproduce anything.** It is an
environment fault, not a Vinyl defect, so no code change was made — killing the stale
process (`kill 1672`) resolves it. Flagged for the owner as a decision:

- pointing the default at `127.0.0.1` would make Vinyl immune to the IPv6-first trap, but
  would break anyone whose Ollama binds only IPv6 — a real trade-off, not a free win.

The `describe_shape` diagnostic added in this batch is what makes these two causes
distinguishable in a log next time: a `'{'` start under the cap is the shape bug, a
timeout is the endpoint.

### W2 · `auto` template

Two independent defects.

**(a) The save always fails.** `api_set_meeting_template`
(`summary/template_commands.rs:288`) validates any non-empty id with
`templates::get_template(id)`. `auto` is a *reserved* id that deliberately has no file on disk
(`templates/loader.rs:128`, `summary/outline.rs:42`), so `get_template("auto")` always errors
and every attempt to persist Auto is rejected. Guard the validation:

```rust
if !templates::is_reserved_template_id(id) {
    templates::get_template(id).map_err(…)?;
}
```

**(b) "Auto is never selected" — NOT REPRODUCED; no fix shipped.**

The original hypothesis was that `api_suggest_template_for_title` donates a prior
same-title meeting's `template_id`, so recurring meetings re-inherit the pre-1.17
`standard_meeting` default forever. A migration was written to clear it. **The evidence
refutes this and the migration was removed before it shipped:**

- `template_id` distribution in the owner's dev DB: **28 of 29 meetings are already
  `NULL`**; exactly one carries `standard_meeting` (and it has a summary). The donation
  path therefore has almost nothing to donate.
- The **backend default is already Auto**:
  `templates::DEFAULT_SUMMARY_TEMPLATE_ID == outline::AUTO_TEMPLATE_ID == "auto"`,
  applied at `summary/commands.rs:378` and `:559` whenever `template_id` is NULL.
- The **frontend default is already Auto** and is regression-tested — `useTemplates.test.ts`
  covers both "defaults new meetings to Auto" and "keeps the default when no template is
  persisted (NULL)".
- `api_set_meeting_template` is the **only** production writer of `template_id`, and it is
  called only from `useTemplates` (explicit selection or title suggestion).

So with a NULL `template_id`, both the picker and generation already choose Auto.
**W2a alone plausibly explains the entire report**: the owner picks Auto, the save is
rejected, and the preference cannot stick — which reads exactly as "never selected as
default" plus the error toast they quoted.

*A stale doc comment on `api_get_meeting_template` claiming the frontend falls back to
`standard_meeting` (left over from before 0053) is what seeded the wrong hypothesis. It is
corrected in this batch.*

**If it recurs, capture this:** which template name the picker actually displays on a
freshly-opened meeting, and that meeting's `template_id`
(`sqlite3 <db> "select template_id from meetings where id='<id>'"`). Those two facts
separate "the picker shows the wrong thing" from "generation used the wrong thing" — this
investigation could not, because the only reproduction data available was six days stale.

### W5 · Cancelled recurring meetings

**Mechanism.** `GcalEvent` (`calendar/google/sync.rs:852`) does not deserialize `recurrence`
or `recurringEventId`, so the sync cannot distinguish a recurring **series master** from an
expanded instance. `full_sync` requests `singleEvents=true` and only ever sees instances — but
the **incremental** path returns whatever changed, and for a modified recurring series Google
returns the *master*. `map_event` maps it happily (it has `start`/`end`) and upserts it under
`gcal:<cal>/<seriesId>`, creating a phantom row at the series' first-occurrence time.

Cancellations then arrive keyed `<seriesId>_<instanceTs>`, deleting the *instance* row. The
master row can never be matched by that key, so the occurrence stays on the agenda. `full_sync`
would prune it via its replace-all, but it only runs when the 60-day horizon comes within 7
days — roughly every 53 days. The owner's last full sync was 2026-08-10.

**Fix, four parts:**

1. Deserialize `recurrence: Vec<String>` and `recurring_event_id: Option<String>` on
   `GcalEvent`; add `fn is_series_master(&self) -> bool { !self.recurrence.is_empty() }`.
2. Incremental path: a series master is **never** upserted as an event row. Instead delete
   every cached row for that series (`id LIKE 'gcal:<cal>/<seriesId>%'`, escaped) and clear the
   calendar's `sync_token` so the next pass full-resyncs and re-expands instances correctly.
3. A **cancelled** series master deletes by series prefix, not exact id.
4. Migration `20260825000001_force_calendar_resync.sql`: clear `sync_token` and `window_ends_at` for all
   calendars. One full resync per calendar then replaces every row, purging the 384 phantom
   rows already cached.

Plus a drift guard: full-resync at least every 7 days, not only when the horizon nears —
`sync_calendar` treats a `last_synced_at` older than `MAX_INCREMENTAL_DAYS` as unhealthy.

9. `/meetings` offers Month and List; Month shows recorded meetings only, navigates months, and a day click reveals that day's meetings.
10. The sidebar exposes a visible search entry point that opens the palette in search mode.
11. During a live recording, a Prep button opens a drawer showing brief + carried-over open items + prep notes.

## Risks / open questions

- **W1 may not reproduce.** Handled by the gate: diagnostics ship, the fix does not. This is
  the explicit lesson from 0053 and is not to be waived.
- **W1 may be truncation, not shape.** Acceptance criterion 3 forces the reply-length check
  against the 4096 cap before the shape fix is accepted.
- **W2b was dropped on evidence** rather than shipped on a hunch — the same standard the
  W1 gate imposes, applied to W2.
- **W5's `sync_token` clear** costs one full resync per selected calendar on first launch after
  upgrade — a few seconds of network, and it is the intended purge mechanism.
- **W5 prefix delete** must escape `%`/`_` in calendar and series ids (Google ids are
  base32hex, but calendar ids are email-shaped and can contain neither — assert with a test
  rather than relying on it).
- `/meetings` is near the file-size ratchet; W3 must extract the list body, not append.
