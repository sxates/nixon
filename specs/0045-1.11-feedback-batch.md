# 0045 — 1.11 feedback batch: deferred-processing UX (concurrent processing, auto-start, top-level control)

- **Status:** Implemented (pending owner smoke) — full frontend/Rust gates green (569 FE tests, cargo check/clippy, file-size ratchet); whole-branch review clean. Manual smoke (record on battery → reconnect while recording another → auto-process without abort) is the remaining owner check.
- **Owner agent(s):** frontend-engineer (WS1–WS4 UI/controller), rust-core-engineer + audio-engineer (WS1 backend concurrency-safety)
- **Roadmap phase:** follows the `2026-07-21-low-power-mode` design (deferred processing shipped v1.10.2 / v1.11.0)

## Context / Problem

Owner dogfooding v1.11.x surfaced that the **deferred / low-power processing UX**
(designed in `docs/superpowers/specs/2026-07-21-low-power-mode-design.md`) does not fit
real back-to-back-meeting usage. All six reported symptoms trace to a small number of root
causes in the existing implementation:

1. **The "process meetings" prompt is inconsistent on reconnect.** The trigger
   (`frontend/src/hooks/useDeferredBacklog.ts`) is gated on **not recording** *and* a
   long debounce — `AC_TRANSITION_DEBOUNCE_MS = 90_000` on a power→AC transition and
   `ON_MOUNT_GRACE_MS = 120_000` on launch (`frontend/src/lib/deferred-backlog.ts:18–20`).
   `runCheck` bails entirely when `isRecordingRef.current` is true
   (`useDeferredBacklog.ts:471,482`) and `power-source-changed`→AC only schedules a check
   `if (!isRecordingRef.current)` (`:527`). The owner's real pattern — reconnect to power
   *while already in the next meeting* — never even checks for a backlog.
2. **The prompt doesn't say which meetings, or when they're done.** The banner
   (`frontend/src/components/DeferredBacklog/DeferredBacklogPrompt.tsx:70–72`) shows only a
   count ("N meetings recorded without processing"). Completion is a single transient
   `toast.success('Deferred meetings processed')` (`useDeferredBacklog.ts:457`) — no
   per-meeting titles, no live status, easy to miss.
3. **It prompts repeatedly after connecting to power.** Every power→AC transition schedules
   a fresh check and re-raises the banner PROMPT shape; declining only drops to a soft
   BADGE (`DeferredBacklogPrompt.tsx:54–55`) that a later transition can flip back to a
   prompt.
4. **Manual processing doesn't finish, and can't run during a recording.** By design the
   queue passes `shouldAbort: () => isRecordingRef.current` to every pipeline step
   (`useDeferredBacklog.ts:224,244,321`) and *starting* a recording dispatches `abort`
   (`:534–541`). So kicking off processing and then recording/continuing another meeting
   kills it mid-flight — exactly the owner's "if I go away it doesn't finish, and it seems
   like it doesn't work while a recording is in progress."
5. **No prominent, top-level control.** The only affordance is the bottom-center nag pill.
   The prime slot next to `Record` in `TodayHeader` (`frontend/src/components/Today/TodayHeader.tsx:60`)
   has no process button, and a backlog is invisible from other screens.
6. **Wrong empty-state copy.** `VirtualizedTranscriptView.tsx:758` shows the generic
   **"Welcome to Vinyl!"** for any zero-segment, not-recording transcript — including a
   finished-but-unprocessed deferred meeting, where it is misleading.
7. **The per-meeting "Process now" button can be a silent no-op (live bug).** Owner
   (on AC) clicked "Process now" on a battery-recorded meeting: spinner shows, but no
   CPU/GPU activity, and navigating away/back shows nothing in progress. Root cause is two
   coupled defects: (a) the button's spinner is **local set-once state** —
   `handleProcessNow` calls `setProcessRequested(true)` and dispatches the event, but
   nothing ever resets it or reconciles it with the controller
   (`TranscriptButtonGroup.tsx:106–112,211,218`); it lies when the request is dropped and
   is lost on remount. (b) The controller's immediate handler **silently drops the click**
   when `processingRef.current` is true (`useDeferredBacklog.ts:548`, only a
   `console.warn`), and the backend can independently refuse via the
   `RETRANSCRIPTION_IN_PROGRESS` single-flight (`retranscription.rs:16`). So a wedged
   frontend or backend flag turns every click into a dead no-op with a fake spinner. The
   deferred path invokes the backend correctly otherwise (`needsRetranscription` returns
   true for `explicitlyDeferred` meetings, `deferred-backlog.ts:88`), which is why the fix
   is about **honest state + un-wedgeable flags**, not the pipeline itself.

**Decisions (from brainstorming, owner-approved):**
- **Concurrency:** *Always run, accept contention* — decouple processing from recording
  entirely. Processing runs whenever a backlog exists, including during a live-transcribing
  meeting. (Owner explicitly accepted the CPU/battery trade-off.)
- **Nudge model:** *Auto-start + visible status* — when a backlog exists **and on AC
  power**, start processing automatically (no prompt to click), with a persistent
  status/button for manual start/stop. No repeating pop-ups.
- **Placement:** *Today header button + global indicator* — a prominent button top-right of
  the Today view (next to Record) plus a compact status indicator visible from any screen,
  replacing the bottom-center nag pill.

## Goals

- Deferred processing **runs to completion regardless of recording state** — starting or
  continuing a recording never aborts it.
- With a backlog present **and on AC power**, processing **auto-starts** (short debounce),
  with no repeating prompts; on battery it does not auto-start but a manual control is
  available.
- The owner can always see **which meetings** are pending/processing (by title) and a
  **persistent completion state** (not just a transient toast).
- A prominent **"Process meetings"** control lives in the Today header, with a compact
  **global indicator** reachable/visible from any screen.
- The unprocessed-transcript empty state reads correctly ("not processed yet" + a process
  action), never "Welcome to Vinyl!".

## Non-goals

- Re-introducing the 90s/120s debounce prompts or any OS-notification nag (explicitly
  removed).
- Throttling / prioritizing batch work below live STT to *reduce* contention — owner
  accepted contention; if concurrent STT proves unsafe the fix is engine isolation
  (WS1 backend), not throttling.
- Windows/Linux power detection; thermal/CPU-load throttling (unchanged from the low-power
  design's out-of-scope).
- Changing the backend deferred-candidate query semantics
  (`list_deferred_candidates`, `frontend/src-tauri/src/database/repositories/meeting/query.rs:48`)
  or the retention exemption (`audio/retention.rs:84`).

## Approach

The controller (`useDeferredBacklog.ts`) currently couples three concerns: *when to run*
(power/recording/debounce), *what the pipeline does* (retranscribe→diarize→summarize), and
*how it's surfaced* (the nag pill). This batch **removes the recording coupling**, **replaces
the prompt-and-debounce trigger with an auto-start-on-AC decision**, and **moves surfacing to
a top-level button + global indicator with per-meeting status**. The heavy pipeline itself
(`processMeeting`, the backend commands, the persisted `meetings.processing_mode` marker,
retention exemption) is reused unchanged. Trigger/queue logic is extracted into a new pure
module so `useDeferredBacklog.ts` stays under the 800-line ratchet and the decision is
unit-testable.

## Design

### WS1 — Decouple processing from recording (frontend-engineer; backend concurrency-safety: rust-core-engineer + audio-engineer)

**Frontend.** Remove every `isRecording` gate from the queue:
- Delete the record-start `abort` dispatch (`useDeferredBacklog.ts:534–541`) and the
  `processingRef`/recording interplay that stops the queue.
- Remove `shouldAbort: () => isRecordingRef.current` from all pipeline steps
  (`:224,244,321`) and the between-step re-checks (`:351,362,367`). The abort predicate
  becomes user-initiated stop only (WS3) plus the existing per-step timeout ceilings
  (`RETRANSCRIPTION_TIMEOUT_MS`/`SUMMARY_TIMEOUT_MS`/`DIARIZATION_TIMEOUT_MS`,
  `:60–62`).
- Remove the `runCheck` recording bail (`:471,482`) and the `!isRecordingRef.current`
  guard on the power→AC schedule (`:527`).
- `isRecordingRef` / `useRecordingState` usage is dropped from the controller unless still
  needed for the auto-start power read.

**Un-wedgeable flags (fixes the live silent-no-op bug, symptom 7).** Guarantee neither the
frontend queue flag nor the backend single-flight can permanently dead-drop a request:
- Frontend `processingRef` already resets in a `finally` (`:429–431`) — audit that no path
  sets it true without entering that `try`, and that React effect re-mounts / strict-mode
  double-invoke cannot leave a stale `true`. The recording-abort path removed in WS1 is a
  prime suspect for leaving state inconsistent; verify it's gone cleanly.
- Backend `RETRANSCRIPTION_IN_PROGRESS` (`retranscription.rs:16`) must be a strict RAII
  guard released on **every** exit (success, error, panic, early return) — audit
  `start_retranscription_command` (`:718`) for any early-return before the guard is armed
  or any path that leaves it set. Add a reproduction test if a leak path exists.
- **Reproduce first (systematic-debugging):** before fixing, add a failing test that drives
  the immediate-process path with the guard pre-set and asserts the click is not silently
  lost (it either runs or is honestly reported as busy/queued).

**Backend concurrency-safety (must verify before shipping WS1).** Determine whether a
batch retranscription (`frontend/src-tauri/src/audio/retranscription.rs`,
`start_retranscription_command:718`) and a live-transcribing meeting can run at the same
time without sharing a single Whisper/Parakeet + Metal context (a shared context would be a
**crash/UB**, not just slowness). Trace engine construction on both paths
(`whisper_engine/`, `parakeet_engine/`, `audio/transcription/worker.rs` vs. the
retranscription path). If they share a resident model/context, give the backlog path its
own engine instance (or serialize *only* the GPU-critical section) so concurrent live +
batch STT is safe. The existing `RETRANSCRIPTION_IN_PROGRESS` single-flight
(`retranscription.rs:16`) stays — it prevents two *backlog* jobs colliding, which is still
correct.

### WS2 — Auto-start trigger (frontend-engineer)

New pure module `frontend/src/lib/backlog-autostart.ts` (keeps the hook small, unit-testable):

- `decideAutostart({ backlogCount, onBattery, isProcessing }): boolean` — returns true iff
  `backlogCount > 0 && !onBattery && !isProcessing`.
- `AUTOSTART_DEBOUNCE_MS = 5_000` (a short blip-absorbing debounce, replacing the 90s/120s
  constants in `deferred-backlog.ts`, which are deleted along with `shouldPromptBacklog`).

Controller changes (`useDeferredBacklog.ts`):
- On each relevant signal — app mount, `power-source-changed`, and a deferred recording
  finishing (the existing `process-deferred-meeting-now` / stop-mark paths) — re-query
  `api_get_power_state` + `api_list_deferred_meetings`, then if `decideAutostart(...)` →
  `runQueue()` after the short debounce.
- **On battery:** never auto-start; the manual button (WS3) still calls `runQueue()`
  directly (owner may force it).
- **During recording:** no special-casing — auto-start proceeds (per the concurrency
  decision).
- Resilience: the controller stays mounted app-globally (already is, via
  `frontend/src/app/layout.tsx`), so it survives in-app navigation. App quit / system sleep
  stops the queue; the persisted `meetings.processing_mode='defer'` marker means the next
  mount/AC signal resumes remaining meetings. An interrupted meeting keeps its marker.

### WS3 — UI: Today button + global indicator + status list (frontend-engineer)

Replace the nag pill with a status model driven by the controller. Expose from
`useDeferredBacklog` (or a thin context) a `backlog` view: `{ items: {meetingId, title,
status}[], activeIndex, isProcessing }`, where `status ∈ waiting | transcribing | diarizing
| summarizing | done | error`. Per-meeting title comes from `api_list_deferred_meetings`
(extend it to include the meeting title/date if it does not already).

- **`TodayHeader`** (`components/Today/TodayHeader.tsx`): new control in the right-hand
  action cluster (line ~36), rendered only when `items.length > 0`:
  - Idle backlog → **"Process N meetings"** → `runQueue()`.
  - Running → **"Processing… (k of N)"** with the active meeting's title; click opens the
    detail popover; a Stop affordance sets the user-initiated abort.
- **Global indicator:** a compact chip mounted where `DeferredBacklogPrompt` was
  (`app/layout.tsx:285`), visible on any screen, showing count (idle) or progress
  (running). Click routes to Today / opens the detail popover. `DeferredBacklogPrompt.tsx`
  (PROMPT/BADGE/PROGRESS pill) is removed.
- **Detail popover:** lists each backlog meeting **by title** with its live per-meeting
  status (Waiting → Transcribing → Diarizing → Summarizing → **✓ Done** / ⚠ Error).
  Completed items **remain visible** for the session instead of a one-shot toast, directly
  answering "which meetings / when done." Includes Process-all and Stop.
- The transient completion `toast.success` (`useDeferredBacklog.ts:457`) is replaced by the
  persistent Done state (a single non-repeating summary toast on full-queue completion is
  optional, not required).
- **Single source of truth (fixes symptom 7).** Every process affordance — the new
  Today-header button, the global indicator, AND the per-meeting **`TranscriptButtonGroup`
  "Process now"** — derives its spinner/label from the controller's backlog view model, not
  local component state. Delete `TranscriptButtonGroup`'s `processRequested` set-once local
  state (`:108,211,218`); it reads that meeting's status from the shared backlog state so a
  navigate-away/return re-renders the real in-progress status, and a dropped request never
  shows a fake spinner.
- **Honest busy handling.** Clicking "Process now" while the queue is already running must
  **enqueue** that meeting (or focus it if already queued) rather than the current silent
  drop at `useDeferredBacklog.ts:548`. The controller exposes an `enqueue(meetingId)` that
  appends to the running queue; the button reflects "Queued" until it becomes active.

### WS4 — Unprocessed-transcript empty-state copy (frontend-engineer)

Make the zero-segment empty state context-aware instead of always "Welcome to Vinyl!":
- In `VirtualizedTranscriptView.tsx` (empty-state block at `:737`, not-recording branch at
  `:756–760`), when the meeting is an unprocessed deferred/sparse recording (has audio;
  `processing_mode='defer'` or sparse transcript), show **"This recording hasn't been
  processed yet."** + a **Process now** action (reuse the existing
  `process-deferred-meeting-now` CustomEvent / `TranscriptButtonGroup` "Process now" path).
- Only a genuinely fresh view (no recording, no audio) keeps a welcome / "Start recording to
  see live transcription" message.
- Mechanism: the meeting-details panel (`components/MeetingDetails/TranscriptPanel.tsx`)
  renders `VirtualizedTranscriptView` **directly**, so it is not on the record-page's
  `transcriptEmptyStateVariant` path today. Compute the unprocessed/deferred/sparse
  condition in a shared helper (extend `frontend/src/lib/processing-mode.ts`) and pass an
  explicit empty-state variant/prop into `VirtualizedTranscriptView`, so its
  "Welcome to Vinyl!" branch (`:756–760`) is reached **only** for the true fresh case and
  the unprocessed case renders the new copy + Process-now action. Avoid a bare inline
  string so the branch selection is unit-testable.

### Data model

None. Reuses `meetings.processing_mode` and the existing deferred-candidate query. If
`api_list_deferred_meetings` does not already return meeting title/date, extend its
projection (no schema change) — verify during implementation.

### Tauri IPC

No new commands expected. Reuses `api_get_power_state`, `api_list_deferred_meetings`
(possibly widened projection), `start_retranscription_command`, `api_diarize_meeting`,
`api_process_transcript`, `api_set_meeting_processing_mode`, and existing completion events.
Any backend engine-isolation from WS1 is internal (no new IPC).

## Acceptance criteria

- Starting or continuing a recording while a backlog is processing does **not** abort the
  queue; processing completes (verified by test with the recording flag toggled true
  mid-queue).
- With `backlogCount > 0`, `onBattery = false`, `isProcessing = false`,
  `decideAutostart` returns true; on battery it returns false (unit-assertable). No PROMPT
  banner is ever shown; auto-start fires within the short debounce.
- The Today header shows a "Process N meetings" button when a backlog exists and
  "Processing… (k of N)" with the active meeting's title while running; the detail popover
  lists each meeting by title and shows a persistent ✓ Done per meeting.
- The global indicator is visible from a non-Today screen when a backlog exists/processes.
- A finished, unprocessed deferred meeting's transcript pane reads "This recording hasn't
  been processed yet." with a working Process-now action — never "Welcome to Vinyl!".
- Concurrency-safety: with WS1b, a batch retranscription running during a live-transcribing
  meeting does not crash (manual smoke + any added Rust test around engine construction).
- **Silent-no-op fix (symptom 7):** clicking "Process now" always results in real work or an
  honest "Queued"/"Busy" status — never a fake spinner over no activity. Its spinner survives
  a navigate-away/return because it reads controller state. With the frontend/backend flags
  pre-set, a reproduction test asserts the click is not silently dropped, and the flags are
  proven to always release (finally/RAII).
- Definition of Done per `/CLAUDE.md`: `cargo check`/`clippy`/`test`, `pnpm lint`/`test`,
  file-size ratchet (`scripts/check-file-size.sh`) — new trigger logic lives in
  `lib/backlog-autostart.ts` so `useDeferredBacklog.ts` does not cross 800 lines. Known
  `vad_filter` failure stays exempt.

## Risks / open questions

- **Concurrent STT contention is real and accepted.** If WS1b finds the engines *cannot* be
  safely isolated on this GPU/model without unacceptable effort, fall back to serializing
  the GPU-critical STT section (batch waits behind the live frame) — still "always runs,"
  just not literally simultaneous decode. Flag to owner if this changes perceived behavior.
- **Auto-start on AC during a live meeting** will spin up heavy work mid-meeting the moment
  you plug in. This is the accepted trade-off; the visible status makes it non-surprising.
  Watch-for: live-transcript latency/quality degradation during concurrent backlog runs.
- **`api_list_deferred_meetings` projection** may need widening for titles — confirm it has
  no perf cost on large libraries.
- Removing `DeferredBacklogPrompt` must not orphan its listeners (`process-deferred-meeting-now`
  is also dispatched by `TranscriptButtonGroup` and stop-mark paths) — keep those handlers on
  the controller.
