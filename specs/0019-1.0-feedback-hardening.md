## Context / Problem

Live testing of the 1.0 release during real meetings on 2026-06-29 produced a batch of
~24 issues spanning data loss, recording-lifecycle reliability, identity/diarization UX,
and surface polish. This spec synthesizes that feedback, grounds each item in the current
code, and sequences the work by severity.

The batch breaks into **eight workstreams**. WS6 (recording lifecycle) contains a **P0
data-loss bug** (a finished meeting is silently deleted) and should ship first. The larger
feature workstreams (WS4 templates, WS5 search/Ask-AI) are big enough to graduate into their
own numbered specs once approved — this doc captures their shape and the integration points.

Two items here were already in `specs/BACKLOG.md`: "Join & Record adopts calendar identity"
(now **fully landed** — title + `calendar_event_id` + attendees seeded onto the live
recording; see WS6.3 ✅) and is folded in below.

## Goals

- Eliminate the data-loss path; make the record→stop→reopen loop reliable across both manual
  stop and Zoom auto-stop, including races between them.
- Make a recording's relationship to its calendar event and home-screen state correct and visible.
- Move speaker→person identity work into the transcript itself; remove redundant confirmations;
  allow per-segment correction and automatic consolidation of duplicate identities.
- Make the People/participants surfaces compact and searchable.
- Surface and complete the template system; make search real; add cross-meeting Ask-AI.
- Ship-hygiene: real waveform, custom dictionary, hide dev-only prototype in release.

## Non-goals

- Rewriting the meetily audio capture / mixing / VAD pipeline (kept per `/CLAUDE.md`).
- A general "merge any two people" identity-graph editor beyond what consolidation needs (the
  owner-only `merge_person_into_owner` is the current mechanism; WS2.4 scopes the minimum).
- Replacing the diarization model or live-diarization architecture (ADR-0006); WS2.6 only
  changes whether live results are *preserved*, not how they're computed.

## WS6 — Recording lifecycle & calendar integration (P0/P1)

> Owner: rust-core-engineer + frontend-engineer. The reliability core of the product.

### WS6.1 — P0: finished meeting silently deleted ("doesn't exist" / disappeared)

**Problem (note 22):** After a real meeting, reopening it errored ("doesn't exist"); the
meeting was gone from home and from the recordings folder; upcoming iCal meetings also
vanished from home.

**Root cause:** `frontend/src/hooks/useRecordingStop.ts:298-339` — the "abandoned recording"
cleanup calls `api_delete_meeting` (`:321`) whenever a stopped recording has
`freshTranscripts.length === 0` and no typed notes. A Join-&-Record meeting that ends quickly
(Zoom auto-stop after the 3s join delay, a short call, or transcripts not flushed in time) hits
this and gets its **calendar-linked row deleted** → `get_meeting` returns `RowNotFound`
(`database/repositories/meeting.rs:236`) on reopen. Because the row's `folder_path` was never
persisted at create time (both `calendar.ts:244` pre-create and
`useRecordingStart.ts:83 createMeetingForRecording` leave it NULL), `api_delete_meeting`'s
folder cleanup (`api/api.rs:872-893`) reads NULL and removes nothing — so audio is **orphaned
on disk** while the DB row is gone. Contributing races: the `stopInProgressRef` early-return
(`useRecordingStop.ts:141-144`) when manual-stop and Zoom-auto-stop both fire, and the
transcription-flush / deferred-event waits (`:166`, `:222`, `:262-265`).

**Approach:** Never auto-delete a meeting that the user did not explicitly discard. Specifically:
- Don't delete a row that has a `calendar_event_id`, or that has on-disk audio, or that was
  created < N seconds ago, on the zero-transcripts path. Convert "abandoned cleanup" into an
  explicit user action (ties to the BACKLOG "delete a started/recorded meeting" item) rather
  than an automatic side effect of an empty stop.
- Persist `folder_path` onto the meeting row at **start** (in `api_create_meeting` /
  `MeetingsRepository::create_meeting`) so reopen, cleanup, and delete are consistent and audio
  is never orphaned.
- Reconcile the double-mounted `useRecordingStop` (mounted both globally in
  `contexts/RecordingPostProcessingProvider.tsx:28` via `layout.tsx:254` and on
  `record/page.tsx:104`) and the `stopInProgressRef` guard so a stop that loses the
  manual-vs-auto race still finalizes/saves instead of stranding an empty NULL-folder row.

**Files:** `frontend/src/hooks/useRecordingStop.ts:298-339`,
`frontend/src-tauri/src/api/api.rs:1144` (`api_create_meeting`),
`frontend/src-tauri/src/database/repositories/meeting.rs:45` (`create_meeting`, persist
`folder_path`), `frontend/src-tauri/src/audio/recording_saver.rs` (folder init).

### WS6.2 — P1: lingering floating "recording" UI after Zoom ended

**Problem (note 20):** Zoom ended, Vinyl wrapped up the meeting, but the bottom floating
"meeting recording" widget stayed.

**Current:** `frontend/src/components/GlobalRecordingBar.tsx:92` renders while
`sessionInFlight = isRecording || isStopping || isProcessing || isSaving`. The post-stop
pipeline (transcription wait up to 60s, 4s late-segment wait, 5s deferred-event race in
`useRecordingStop.ts`) keeps the bar in "Finishing up…" long after Zoom ended; and if a branch
sets SAVING/PROCESSING but an error path doesn't reset to IDLE, the bar never clears.

**Approach:** Guarantee a terminal `IDLE`/`ERROR` status in **every** branch of
`handleRecordingStop`; keep the bar's visibility predicate but ensure status reliably reaches a
terminal state. Consider a max-duration watchdog that forces IDLE if post-processing exceeds a
bound. Files: `frontend/src/hooks/useRecordingStop.ts`, `GlobalRecordingBar.tsx:90-98`.

### WS6.3 — P1: calendar event association (title + attendees), update the event's recording

**Problem (note 21):** Joining from a calendar event produced a generic date-time meeting with
no attendees, divorced from the event. Want: the calendar item *becomes* the recording (adopts
title + attendees), not a separate meeting. (On a later run the home "Recent Recordings" entry
did show the event title, but the in-progress recording still showed date-time + no participants.)

**Current:** `calendar.ts:229 joinAndRecord()` now pre-creates the row with `meetingTitle:
event.title` and `calendarEventId: event.id` (`:244-250`), and `useRecordingStart.ts` adopts it
via `consumePendingJoinMeeting()`. **Gaps:** (a) `JoinAndRecordEvent` (`calendar.ts:150`) carries
no attendees — the roster is only seeded lazily on first meeting-details view via
`resolve_attendees_for_meeting()`/`api_get_meeting_attendees` (`diarization/commands.rs:447-512`,
EventKit lookup by stored `calendar_event_id`), so the *in-progress* recording shows none. (b) If
the pre-create `invoke` throws (`calendar.ts:255`, common on the EventKit-less dev binary), it
falls through to a generic date-stamped row with no `calendar_event_id` — reproducing the original
symptom exactly. (c) No dedupe: joining the same event twice creates two rows.

**Approach:** Carry attendees on `JoinAndRecordEvent` and seed participants synchronously at
create (so the live recording shows title + roster immediately); make the calendar→recording
link the same logical object (dedupe by `calendar_event_id` — reuse the existing row instead of
creating a second); harden the degrade path so a failed pre-create still links the event. Files:
`frontend/src/lib/calendar.ts` (`JoinAndRecordEvent`, `joinAndRecord`),
`frontend/src/hooks/useRecordingStart.ts` (`createMeetingForRecording`),
`frontend/src-tauri/src/api/api.rs:1144` + `MeetingsRepository` (optional synchronous participant
seed; today `api.rs:1183-1186` explicitly does not seed).

**Status: ✅ DONE.** Implemented frontend-only by reusing the existing seed (`api_get_meeting_participants` seeds `meeting_participants` from the linked event idempotently)
and create (`api_create_meeting` already accepts `calendarEventId`/`startedAt`):
- **gap a** — `joinAndRecord`/`createMeetingForRecording` now call `seedMeetingParticipants()`
  the moment the calendar-linked row exists, so the *live* recording shows attendees without
  waiting for the Participants popover.
- **gap b** — `PendingJoinMeeting` now always carries the calendar link (`calendarEventId` +
  `startsAt`) with a **nullable `id`**. A failed up-front create stashes `id: null` + the link, so
  the recorder creates the row itself **with** `calendarEventId` — keeping the title + roster
  instead of degrading to a date-stamped meeting (the exact original symptom).
- **gap c** — `peekPendingJoinMeeting()` makes a second Join & Record on the same event during the
  pre-record delay a no-op. Cross-session dedupe is **deliberately skipped**: recurring-event
  occurrences can share an EventKit id, so merging by it would wrongly fold separate recordings.

Tests: `calendar.test.ts` (degrade-path shape + peek), `useRecordingStart.test.ts` (linked-row
create + roster seed on adopt and degrade). Not visually verifiable headlessly (needs live
Zoom + EventKit); covered by the hook/lib tests.

### WS6.4 — P1: recording state on home; don't offer "Join & Record" while recording

**Problem (note 23):** A recording in progress should be visible on home; a "happening now"
event should show "Recording…", not "Join & Record".

**Current:** `DayAgenda.tsx:325 canJoin = !!item.zoomUrl && !status.recorded && !isRecordingThis`
only suppresses Join & Record on the row matched to the live recording (`recordingThisId`,
`:753-766`, by `currentMeetingId` then title). A *different* happening-now event still shows
Join & Record while you record another; matching is title-based and fragile.

**Approach:** When any recording is in flight (`useRecordingState().isRecording`), suppress
Join & Record across all agenda rows and show a global "Recording in progress" affordance;
keep "Return to recording" on the matched row. Tighten row-to-recording matching to prefer the
persisted `calendar_event_id` over title. Files: `frontend/src/components/Calendar/DayAgenda.tsx`,
`frontend/src/lib/calendar.ts:236-237` (already guards double-start).

**Status: partially DONE** — the Join & Record suppression is implemented + unit-tested:
`canJoinAgendaItem()` (`lib/day-agenda.ts`) returns false while *any* recording is in progress,
wired into `DayAgenda` `AgendaRow`'s `canJoin` (tests in `day-agenda.test.ts`). The matched row
already shows "Recording…/Return to recording". Remaining: a dedicated global home banner and
preferring `calendar_event_id` over title for row↔recording matching.

### WS6.5 — P1: navigating to a previous meeting redirects to the active recording

**Problem (note 24):** While recording, opening a previous meeting navigated to the
currently-recording meeting instead.

**Current:** `meeting-details/page.tsx:41-53` redirects to `/record` only when

### WS6.6 — P1: persistent system notification at meeting start with "Join & Record"

**Problem (note 14):** When a meeting time starts, want an OS notification ("a meeting has
started") with a "Join & Record" button that **persists until interacted with or dismissed**.

**Current:** `CalendarAlerts.tsx` fires a **one-shot** native notification 2 min before start
(`LEAD_MS`, `:49`) wired to `joinAndRecord` via the "Record" action button. OS notification is
not sticky; the in-app Zoom-detected sonner toast *is* persistent (`duration: Infinity`) but is
Zoom-process-driven, not clock-driven. There's no persistent start banner.

**Approach:** Add a clock-driven, persistent alert at the event start time with a "Join &
Record" action; reuse `lib/osNotification.ts notify()` action plumbing. Files:
`frontend/src/components/Calendar/CalendarAlerts.tsx`, `frontend/src/lib/osNotification.ts`.

**Status: NOT a persistent in-app banner — needs an out-of-app solution (see below).** An
in-app persistent banner was prototyped and **reverted**: the whole value of a start
notification is reaching the user when Vinyl is **not focused** (they're in Zoom/another app),
and a `duration: Infinity` sonner toast is just in-app clutter the user must keep dismissing.
The clock-driven start alert must live at the **OS** layer.

**Follow-up to spec (`specs/00XX — out-of-app meeting-start notification`):** design a real OS
notification fired at event start (clock-driven, distinct from the existing 2-min lead
`notify()` one-shot) with a working "Join & Record" action button that survives the app being
backgrounded. Open questions to resolve in that spec:
- **Persistence:** macOS `UNNotification`s aren't truly "sticky"; they sit in Notification
  Center until dismissed but don't re-alert. Decide between (a) accepting Notification-Center
  persistence, or (b) a bounded **re-notify** cadence (e.g. re-fire every N min up to a cap
  until joined/dismissed) — the closest cross-platform approximation of "until interacted with".
- **Action delivery while backgrounded:** confirm the notification's "Join & Record" action
  routes back into the app and triggers `joinAndRecord` even when Vinyl is backgrounded/closed
  (Tauri notification action handlers + app-focus/relaunch). The current `notify()` plumbing is
  built for the focused/lead case; verify the backgrounded path end-to-end.
- **De-dupe vs. the lead alert:** the 2-min lead notification and the at-start notification are
  two events for one meeting — de-dupe independently (separate fired-set keys), and suppress the
  start alert if a recording for that meeting is already underway.
- **Scope:** joinable (`zoomUrl`) meetings only, so plain calendar blocks don't notify.

Owner: frontend-engineer + (Tauri notification plumbing). No code in this pass beyond keeping
the existing lead-time `notify()` one-shot intact.

### WS6.7 — P0: consecutive recordings merge into one meeting; the other's transcript is lost

**Problem (reported 2026-06-29, follow-on):** A saved meeting's transcript shows text from two
different recording sessions interwoven by time; "Open folder" shows only one session's files.
A second affected meeting has its own on-disk recording folder but **no transcript in the UI and
no way to re-transcribe** — its transcript text was absorbed into the first meeting.

**Root cause (confirmed by tracing both layers):** A second recording session reuses the *first*
session's DB `meeting_id` (held in `currentMeeting.id`), and the backend save then **blindly
appends + overwrites**:
- Frontend: `useRecordingStop.ts` never resets `currentMeeting` to `PLACEHOLDER_MEETING_ID` on
  the **success** path — on save it sets `currentMeeting` to the just-saved id (`:446-455`) and
  leaves it there (contrast the abandoned path, which resets at `:344-350`). The comment at
  `:290-292` ("currentMeeting stays the placeholder") is wrong for every recording after the
  first. If the next session's `createMeetingForRecording` is skipped — `meetingCreatedRef` not
  reset (`useRecordingStart.ts:71,107-111`), `api_create_meeting` throws (`:94-101`), or a stale
  `PENDING_JOIN_MEETING_KEY` is adopted (`:76-80`) — session B's stop computes
  `existingMeetingId = A`.
- Backend: `TranscriptsRepository::save_transcripts_for_meeting`
  (`database/repositories/transcript.rs:109`) **appends** segments with no
  `DELETE … WHERE meeting_id = ?` (`:147-148`), and **overwrites** `folder_path` to the latest
  session's folder (`UPDATE meetings SET … folder_path = ?`, `:124-132`). The doc comment at
  `:105-108` ("one save per stop … harmless") encodes the broken assumption.
- Display: `get_meeting_transcripts_paginated` orders by `audio_start_time ASC`
  (`meeting.rs:340-348`); both sessions' times start near 0, so rows interleave totally.
- Net: meeting A holds A+B transcripts; `folder_path(A)` = B's folder; session A's folder is
  orphaned on disk; if no row B was ever created, B has no DB row at all (the "lost transcript,
  separate folder" half). **No UNIQUE/UPSERT** merges rows — reuse is purely the stale id value.

**Approach (two layers, defense in depth):**
2. *Backend safety net* — ✅ **DONE** (this branch). `save_transcripts_for_meeting`
   (`transcript.rs:109`) now checks for existing transcripts **before** any UPDATE: if the target
   meeting already holds a session's transcripts, it refuses (rollback, loud `error!`) and returns
   `Ok(false)`, so `api_save_transcript` routes the new session to a **fresh meeting row**. The
   populated meeting's transcripts, `title`, `folder_path`, and `calendar_event_id` are left
   untouched — killing all three symptoms (merge, folder overwrite, stale-event attendees) at the
   point of corruption. Regression: `tests/db_lifecycle.rs::second_session_does_not_merge_into_populated_meeting`
   asserts all three invariants and passes only with the fix.
   **Why this also fixes the frontend drift:** the stop success path sets `currentMeeting` from the
   **backend-returned** `meeting_id` (`useRecordingStop.ts:444-449`); since the backend now returns
   the new row's id, the frontend self-corrects.
1. *Frontend root cause (remaining, needs GUI verification):* still worth hardening so a stale id
   never reaches save — reset `currentMeeting` on the failure path of `createMeetingForRecording`
   (`useRecordingStart.ts:94-101`), always clear `PENDING_JOIN_MEETING_KEY`, and make the
   `meetingCreatedRef` reset robust (prevents *notes* — not transcripts — autosaving to a stale
   meeting during the next recording, which the backend net does not cover).
3. *Recovery (remaining):* a repair pass to detect orphaned recording folders (on disk, no linked
   DB row) and re-link / re-transcribe them; the audio is intact, so the lost transcript is
   recoverable. Needs a "re-transcribe from folder" command + user choices on which row keeps
   which transcript — deferred (do not run destructive repair unattended).

**Files:** `frontend/src/hooks/useRecordingStop.ts` (success-path reset, `existingMeetingId`),
`frontend/src/hooks/useRecordingStart.ts` (`meetingCreatedRef`, pending-key, create), 
`frontend/src/lib/calendar.ts` (pending-key clear),
`frontend/src-tauri/src/database/repositories/transcript.rs:109-148` (authoritative save),
`frontend/src-tauri/src/api/api.rs` (re-transcribe-from-folder / repair command).
**Regression test:** the multi-session scenario belongs in the new test harness (`specs/0023`):
record two sessions back-to-back → assert two distinct meeting rows with disjoint transcripts and
stable, distinct `folder_path`s.

## WS1 — Meeting view & live-transcript UX (P2)

> Owner: frontend-engineer.

### WS1.1 — Sticky meeting navigation (note 1) — ✅ DONE

The Summary/Transcript/Notes tab strip (the in-page navigation) scrolled away with the rest of
the column. Fixed: the tab strip in `meeting-details/page-content.tsx` is now
`sticky top-0 z-10 bg-background`, so it pins to the top of the scroll column and stays reachable
from deep in a long transcript. Verified via the `run-vinyl` driver (Transcript tab + scroll 1400px
→ tabs remain pinned). The title/back row still scrolls (a single back gesture); the tabs are the
recurring nav and are what stays.

### WS1.2 — Live transcript shouldn't jump to bottom on new segments (note 16) — ✅ DONE

**Fixed:** the scroll handler used one 100px threshold for both following *and* re-attaching, so
scrolling up slightly still re-enabled auto-follow and yanked the view down. Introduced
hysteresis via a pure, unit-tested `nextAutoFollow()` (`lib/auto-scroll.ts`): re-attach only when
essentially at the bottom (`AT_BOTTOM_THRESHOLD_PX`), detach once scrolled up past
`SCROLLED_UP_THRESHOLD_PX`, keep state in between. Wired into `useAutoScroll`'s scroll handler;
the new-segment follow guard is unchanged. Tests in `lib/__tests__/auto-scroll.test.ts`.

Original analysis below.


Auto-scroll lives in `frontend/src/hooks/useAutoScroll.ts:131-177`. A "user scrolled up" guard
exists but re-enables auto-scroll whenever the user is within `SCROLL_THRESHOLD = 100px`
(`:22`, `:109-117`) of the bottom — too generous with tall segments, so reviewing earlier
transcript still gets yanked down. Approach: once the user scrolls up, **stay** detached until
they explicitly return to bottom (e.g. a "Jump to live ↓" affordance), rather than
auto-re-enabling on proximity. Tighten/replace the re-enable branch and consider a "new
segments below" pill.

### WS1.3 — Waveform driven by real audio (note 17)

All three recording-surface waveforms are **synthetic**: `record/page.tsx HeaderWaveform`
(`:52-79`, sine), `RecordingControls` bars (`:289-303` `Math.random` interval →
`RecordingControls.tsx:470-482`), and `GlobalRecordingBar.tsx Waveform` (`:212-239`, sine). Real
levels already exist via the Tauri `audio-levels` event consumed by
`AudioLevelMeter.tsx`/`DeviceSelection.tsx:82` (`rms_level`/`peak_level`; Rust
`audio/level_monitor.rs`). Approach: subscribe the recording waveforms to `audio-levels` and
drive bar heights from RMS/peak instead of the synthetic generators.

### WS2.1 — Inline speaker→person assignment in the transcript (note 3) — ✅ DONE

**Fixed.** `TranscriptPanel` now owns a single `useSpeakers` controller shared by the
`SpeakerLegend` (refactored to take it as a prop) and the new
`InlineSpeakerAssign` (`components/MeetingDetails/InlineSpeakerAssign.tsx`), so assigning

by the segment's `speakerKey`).

### WS2.2 — Skip "looks like X" confirmation when assigning a known person (note 7) — ✅ DONE

**Fixed** (`hooks/useSpeakers.ts`): assigning a speaker to a known person (`assignPerson`) or
calendar attendee (`assignAttendee`) now auto-dismisses that speaker's cross-meeting "looks
like X" suggestion, so no confirmation is left hanging after a direct assignment. Covered by
`hooks/__tests__/useSpeakers.test.ts` (suggestion present → assign → suggestion gone, for both
person and attendee; the mock keeps returning it, so the test proves dismissal wins). Original
analysis below.


Three assign paths exist in `SpeakerLegend`: an inline 1:1 calendar suggestion (`:351-362`), a
**"Looks like {name}" cross-meeting voice suggestion that requires confirm** (`:497-533`,
`acceptCrossMeetingSuggestion`), and a **direct assign-to-known-person that already skips
confirmation** (`useSpeakers.ts:276-295 assignPerson` → `api_assign_speaker_to_person`). The fix
is: when the user directly assigns a known person, treat it as confirmed and auto-dismiss any
pending "looks like X" chip for that speaker (`dismissSuggestion`, `useSpeakers.ts:318-337`; gate
at `SpeakerLegend.tsx:497`).

### WS2.3 — Per-segment speaker correction / split (note 8) — ✅ DONE

**Fixed with sticky overrides.** New `transcript_speaker_overrides` table (migration
`20260701000000`) keyed by the **stable `transcripts.id`** records a manual per-line
correction. `TranscriptSpeakerOverridesRepository::set` updates the live transcript AND the
override in one transaction; `reapply()` re-stamps all of a meeting's overrides at the END of
`pipeline::persist`, and persist also unions the override target keys into the materialized
`speakers` rows — so a corrected line **survives re-diarization** (which still clears + rebuilds
everything else) and always resolves to a name. Commands `api_set_segment_speaker` /
`api_clear_segment_speaker` (registered in `lib.rs`); meeting-delete cascades the overrides.
UI: `SegmentSpeakerMenu` — a subtle per-line "This line is…" control (shown on hover) listing
the meeting's speakers, wired through `TranscriptPanel`'s shared controller so the legend +
labels refresh after a move. Covered by `diarization_persistence::segment_speaker_override_survives_rerun` (Rust: holds across a re-run, rejects a cross-meeting line, reverts on clear)
and `SegmentSpeakerMenu.test.tsx`. Verified live via run-vinyl.

### WS2.4 — Auto-consolidate speakers mapped to the same person (note 9) — ✅ DONE

**Fixed (display consolidation).** `SpeakerDto`/`SpeakerModel` now expose `person_id`, and

### WS2.6 — Preserve live diarization to reduce post-meeting work (note 19 — question)

**Answer to the user's question:** live diarization (`diarization/live.rs LiveDiarizer`,
ADR-0006) re-diarizes the growing system channel every 8s with session-stable, "stable-once-
shown" labels — but it is **thrown away** at stop. The offline pass (`pipeline.rs::run`,
auto-triggered from `useRecordingStop.ts:402-414`) calls `clear_meeting_speakers` and is fully
authoritative, overwriting all live labels; the in-memory live registry is dropped
(`recording_commands.rs:236`). **Opportunity:** seed the offline pass from the live registry
(or skip the offline recompute when live coverage is high-confidence) to cut post-meeting
latency. This is a design investigation — propose as its own follow-up if the win is large.

**Conclusion (investigated 2026-06-29) — DEFER, do not implement now.** Confirmed by tracing
both passes: the offline pass isn't just a re-label, it produces outputs the live registry
does not durably provide — (a) authoritative full-audio clustering (live is incremental +
`stable-once-shown`, so an early mislabel is never retroactively corrected), and (b) the
per-remote-speaker **embeddings persisted to `speakers`** that power cross-meeting voice
identity / "Looks like X" (specs/0016 1a). The live `SpeakerRegistry` holds centroids in
memory but is dropped at stop (`recording_commands.rs:236`) and was never wired to persist.

So the two candidate wins carry real regressions for a modest latency payoff:
- **Skip the offline recompute when live coverage is high** → loses retroactive correction
  *and* the persisted cross-meeting embeddings (breaks WS2 identity). Not worth it.
- **Seed the offline pass from the live registry** → only a minor speedup (segmentation +
  embedding inference on the full file still dominate); meaningful plumbing (persist the
  live registry, dedupe keys against the offline clustering) for little gain.

The one genuinely useful, lower-risk slice — **persist the live labels provisionally at
stop** so a just-finished meeting shows speakers immediately while the offline pass refines
in the background — has its own UX risk (labels shifting under the user) and must interact
carefully with `clear_meeting_speakers` and the WS2.3 sticky overrides. **Recommendation:**
spin this out as its own spec (`provisional live labels at stop`) with its own tests; it is
out of scope for this hardening pass. No code change for WS2.6.

## Risks / open questions

- **One spec vs. several:** WS4, WS5, and WS7 are large enough to warrant their own numbered
  specs. Recommend graduating them and keeping this doc as the umbrella/sequencing record.
  *(Confirm with owner.)*
- **WS6.1 cleanup semantics:** Replacing auto-delete with explicit delete needs a UX decision —
  do we keep an empty recording, or prompt to discard? Ties to the BACKLOG "delete a
  started/recorded meeting" item.
- **WS2.3 override persistence:** sticky per-segment corrections vs. an authoritative offline
  pass that wipes keys — needs a small data-model addition (a corrections table or a "manual"
  flag) so re-diarization doesn't clobber user edits.
- **WS2.6:** preserving live diarization changes the "single authoritative correction at stop"
  invariant (ADR-0006); may need a new ADR.
- **WS6.6 persistence:** OS notifications generally can't be made truly sticky cross-platform.
  An in-app banner is NOT an acceptable fallback (it only shows when the app is focused, which
  is exactly when the user doesn't need it, and becomes dismiss-clutter). The follow-up spec
  should resolve persistence at the OS layer (Notification-Center persistence vs. a bounded
  re-notify cadence).
