batch. Several items are **regressions or incomplete follow-through** on `specs/0019` (the 1.0
hardening pass) — they were marked done there but the symptom recurs in real use — so this spec

## Goals

- Make a Zoom call ending behave **identically** to the user pressing "Stop & Summarize":
  stop the audio tap, save once, summarize, no second meeting, accurate duration.
- Keep a calendar-started meeting as **one** object that owns its title, attendees, transcript,
  and recording — never a titled-but-empty row plus a date-time row holding the transcript.
- Persist participants added mid-recording onto the **same** meeting the transcript saves to.
- Make diarization progress actually advance (diagnose the runtime stall, not re-wire).
- Make the home agenda stable (no transient empties) and let the user hide non-meeting items.
- Auto-title ad-hoc meetings from their summary while protecting manually edited titles.
- Replace the scrolling-RMS waveform with a vocal-range spectrometer.
- Surface the AI-summary context field where it's reachable.

## Non-goals

- Rewriting the meetily audio capture / mixing / VAD pipeline (kept per `/CLAUDE.md`).
- Replacing the diarization model or the live-diarization architecture (ADR-0006); WS4 only
  fixes *progress reporting*, not how turns are computed.
- A general contacts/directory integration. WS2.2 (DL expansion) is explicitly bounded by what
  EventKit exposes locally — see Risks.
- Cross-meeting dedupe of recurring-event occurrences by EventKit id (deliberately skipped in
  0019 WS6.3 because recurring occurrences can share an id).

## WS1 — Recording lifecycle: Zoom-end & duration (P0)

> Owner: frontend-engineer + rust-core-engineer. The reliability core.

### WS1.1 — P0: Zoom call-end must perform the full stop (note 3)

**Problem:** When a Zoom call ends, Vinyl stops the transcript but a recording is still running
that the user must manually stop; that manual stop then creates a *second* meeting entry. Zoom
end should be interpreted exactly as clicking **"Stop and Summarize."**

**Root cause (confirmed):** A complete stop is a **two-part** flow — the backend
`stop_recording` command (stops the Core Audio tap, flushes the WAV, emits `recording-stopped`)
**then** `handleRecordingStop(true)` (post-processing + transcript save). The on-page button does
both: `RecordingControls.tsx:295-297` → `:207` `stopRecordingAction` → `:155`
`invoke('stop_recording', …)` then `:166` `onRecordingStop(true)`. The global bar path does both
too (`record/page.tsx:162-163`). **But the Zoom-ended handler calls only the second half:**
`ZoomAutoDetect.tsx:189-194` invokes `window.handleRecordingStop(true)` with **no preceding
`stop_recording`** (and `handleRecordingStop` itself never invokes `stop_recording` —
`useRecordingStop.ts:159-161`). So post-processing/transcript-save runs while the audio tap keeps
capturing. When the user later hits Stop, the full two-part stop runs a *second* save; the backend
WS6.7 safety net (`transcript.rs:133-153`, refuse-to-merge → `Ok(false)`) then routes that second
save to a **brand-new meeting row** (`api/api.rs:1379-1410`) — the spurious extra meeting.

**Approach:** Make Zoom-end call the same complete stop the UI button uses. Route
`ZoomAutoDetect`'s end handler (and any other auto-stop trigger) through a single shared
"stop everything" path that invokes the backend `stop_recording` **then** `handleRecordingStop`,
identical to `stopRecordingAction`. Guard re-entrancy so a near-simultaneous manual stop + Zoom
auto-stop resolves to one stop (the `stopInProgressRef` reconciliation flagged in 0019 WS6.1).

**Files:** `frontend/src/components/ZoomAutoDetect.tsx:176-198`,
`frontend/src/components/RecordingControls.tsx:155-166,207` (`stopRecordingAction` — extract the
shared stop), `frontend/src/hooks/useRecordingStop.ts:159-161` (document/keep the contract),
`frontend/src-tauri/src/zoom/monitor.rs:206-221` (`zoom-meeting-ended` emit — unchanged, just the
consumer changes).

### WS1.2 — P0: meeting duration inaccurate (note 10, e.g. 1h → 1h44m)

**Problem:** Some meetings show durations far longer than reality (a 1-hour meeting as 1h44m).

**Root cause (likely downstream of WS1.1):** The **displayed** duration is audio-time
`MAX(audio_end_time)` over transcript rows (`meeting.rs:114-116`, `:158-160`;
`MeetingIdentityHeader.tsx:58,67-78`; `app/page.tsx:91`). That is normally bounded by the last
transcribed segment — but because the tap is **not stopped at Zoom-end** (WS1.1), it keeps
transcribing for the ~44 min until the manual stop, inflating `audio_end_time` accordingly.
Separately, the wall-clock `get_recording_duration` (`recording_state.rs:351-356`,
`elapsed()`) **includes paused time** and also runs past Zoom-end; it feeds the live
`recordingDuration` and the `total_duration` analytics (`analytics/commands.rs:284-306`).

**Approach:** Land WS1.1 first, then **re-verify** durations on a real call — much of the
inflation should disappear once the tap stops at call-end. For any residual gap: confirm the
displayed duration uses audio-time (it does) and that no surface accidentally shows wall-clock
`get_recording_duration` (which counts pauses) for the *persisted* duration. Add a regression
assertion that a recording stopped at T has `MAX(audio_end_time) ≈ T`.

**Files:** `frontend/src-tauri/src/database/repositories/meeting.rs:114-116,158-160`,
`frontend/src-tauri/src/audio/recording_state.rs:351-373`,
`frontend/src/components/MeetingDetails/MeetingIdentityHeader.tsx:58-78`.

## WS2 — Calendar ↔ meeting identity (P1/P2)

> Owner: frontend-engineer + rust-core-engineer.

### WS2.1 — P1: calendar meeting splits; transcript lands in a date-time row (note 2)

**Problem:** Starting from a calendar event still shows the date-time meeting title (not the
event title) and no attendees during the call. It looks like Vinyl creates a meeting titled after
the event, **plus** a second meeting with the date-time name where the transcript actually lands
(the titled one appears to be removed because it's empty). Want: the transcript + recording +
attendees all live in the **calendar-titled** meeting.

**Root cause (multi-part):**
- The date-time title comes from `generateMeetingTitle()` (`useRecordingStart.ts:50-59`,
  `` `Meeting ${day}_${month}_${year}_…` ``), used whenever there is no `pendingJoin`.
- `joinAndRecord` *does* pre-create a correctly titled, `calendarEventId`-linked row
  (`calendar.ts:311-320`) and stashes a `PendingJoinMeeting` under `PENDING_JOIN_MEETING_KEY`
  (`:333-338`). The recorder is supposed to adopt it (`useRecordingStart.ts:83-90`). **But** if
  the pending key is consumed by a different start path, cleared early, or missed (sessionStorage
  miss / `currentMeeting` reset to the `intro-call` placeholder), the start path falls through to
  the plain create at `useRecordingStart.ts:113-125` and mints a fresh **date-time** row with no
  `calendar_event_id`. The backend never dedupes by `calendar_event_id` (`api/api.rs:1289`,
  `meeting.rs:45` always INSERT).
- The "two meetings, transcript in the date-time one" shape is then completed by the WS6.7 safety
  net (`transcript.rs:133-153`): if the transcript save targets the pre-created calendar row but
  that row is considered already-populated, or the id drifted, the save returns `Ok(false)` and
  the caller routes the transcript to a **new** row (`api/api.rs:1379-1410`) — leaving the
  calendar-titled row empty (and vulnerable to the "abandoned empty meeting" cleanup).

**Approach:**
- **One object, by `calendar_event_id`.** Make the calendar→recording link idempotent in the
  backend: `api_create_meeting` should **reuse** an existing row with the same non-null
  `calendar_event_id` instead of inserting a second (add a lookup; keep recurring-occurrence
  caveat — only dedupe within the active session window, not across days).
- **Adoption must not fall through to a date-time title** when a calendar link exists. Harden the
  pending-join handoff so every start path that can run for a Join-&-Record consumes the same
  pending row (carry the `calendarEventId` on the recording state, not just sessionStorage), and
  prefer `pendingJoin.title` / re-derive the event title over `generateMeetingTitle()`.
- **Seed attendees synchronously at create** so the *live* recording shows the roster (0019
  WS6.3 added `seedMeetingParticipants` at create — verify it still fires before the first
  Participants view; if EventKit is slow, show the event's invitee list optimistically).
- **Don't strand the titled row:** the transcript save must target the calendar row; ensure the
  WS6.7 net never fires for the *first and only* session of a calendar meeting (the row is empty
  at first save, so it shouldn't — confirm the id reaching `existingMeetingId`
  (`useRecordingStop.ts:294-297`) is the pre-created calendar row, not the placeholder).

**Files:** `frontend/src/lib/calendar.ts:291-340`,
`frontend/src/hooks/useRecordingStart.ts:50-59,73-125,206-207,283-284,377-378`,
`frontend/src/hooks/useRecordingStop.ts:294-297,370-375`,
`frontend/src-tauri/src/api/api.rs:1289` (`api_create_meeting` dedupe-by-event),
`frontend/src-tauri/src/database/repositories/meeting.rs:45`.

## WS3 — Participants (P1)

> Owner: frontend-engineer.

### WS3.1 — P1: participant added during recording is dropped at stop (note 5)

**Problem:** A participant added while recording is gone after the recording ends.

**Root cause (ID mismatch, not an overwrite):** During recording, the Participants popover is
rendered with `meetingId={currentMeetingId}` from `TranscriptContext`
(`record/page.tsx:381`, `GlobalRecordingBar.tsx:168`). But `currentMeetingId` there is a
**fabricated client id** — `` `meeting-${Date.now()}` `` set on `recording-started`
(`TranscriptContext.tsx:114-115`) — **not** the SQLite meeting id. The real id lives in
`useSidebar().currentMeeting.id` (set by `createMeetingForRecording`,
`useRecordingStart.ts:118-123`) and is what the transcript saves to and what meeting-details later
reads. So `api_add_meeting_participant` (`diarization/commands.rs:632-679`) writes the new
participant **immediately and durably** — but under the orphan `meeting-<timestamp>` id that
never holds the transcript and is never read again. Nothing overwrites it; it's written to the
wrong meeting. (The stop/save path does **not** touch `meeting_participants` at all — confirmed in
`transcript.rs:121-196`.)

**Approach:** Render the Participants popover during recording against the **real** SQLite meeting
id (`currentMeeting.id`), not the fabricated `TranscriptContext.currentMeetingId`. Either pass the
sidebar's `currentMeeting.id` into the record-screen / global-bar popovers, or reconcile
`TranscriptContext.currentMeetingId` to the real id once `createMeetingForRecording` returns. Add
a guard so adds during the brief window before the row exists are queued/retried, not dropped.

**Files:** `frontend/src/app/record/page.tsx:381`,
`frontend/src/components/GlobalRecordingBar.tsx:168`,
`frontend/src/contexts/TranscriptContext.tsx:114-115`,
`frontend/src/components/Participants/ParticipantsPanel.tsx:158-211` (add handlers).

## WS4 — Diarization progress (P1)

> Owner: audio-engineer.

### WS4.1 — P1: "Identify speakers" still sticks at 0% (note 6) — regression triage

**Problem:** "Identify speakers" shows `Identifying… 0%` for the whole run.

**Finding:** The 0019 WS2.5 wiring is **present and correct in source** — the offline pass calls
the progress variant `diarize_with_embeddings_with_progress`
(`pipeline.rs:405-407`), the `on_progress` closure maps fraction→pct and emits
`diarization-progress` on change (`pipeline.rs:392-404`), sherpa threads the callback to the C
layer (`sherpa.rs:327-455,696-702`), and the frontend faithfully renders the emitted pct
(`useDiarization.ts:86-95`, `TranscriptButtonGroup.tsx:111-114`). So this is now a **runtime**
stall, not a wiring bug. The remaining suspects (in order):
- **sherpa reports `total <= 0`** — the per-chunk callback is guarded by `if total > 0`
  (`sherpa.rs:387`); if the lib reports a non-positive total for this input, no pct beyond the
  initial `pct:0` (`pipeline.rs:355`) is ever emitted.
- **Silent-channel early-return** (`sherpa.rs:343-352` `is_silent`) returns zero turns before any
  per-chunk progress — UI sits at 0% then jumps to complete.
- **Single blocking `compute()`** — all progress is emitted from inside one `compute` call;
  post-`compute` work (re-embedding `sherpa.rs:729`, `merge_clusters_to_at_most` `:738-749`)
  emits nothing. If `compute` itself fires the callback rarely or only at the end, it reads 0%.

**Approach:** Instrument first — log `processed/total` and callback invocation count from
`sherpa.rs:376-395` on a real run to identify which suspect fires. Then the targeted fix: if
`total<=0` or the callback is too coarse, derive progress from chunk indices we control; emit a
small **non-zero "started"** value immediately so it never reads a dead 0%; and add a fallback
**indeterminate** spinner state in the UI when no pct has advanced within N seconds, so the
feature never *looks* hung even on a fast/silent run.

**Files:** `frontend/src-tauri/src/diarization/sherpa.rs:343-352,376-395,387`,
`frontend/src-tauri/src/diarization/pipeline.rs:353-407`,
`frontend/src/hooks/useDiarization.ts:86-95`,
`frontend/src/components/MeetingDetails/TranscriptButtonGroup.tsx:54-114`.

## WS5 — Calendar agenda reliability & control (P1/P2)

> Owner: frontend-engineer + rust-core-engineer.

### WS5.1 — P1: "Upcoming" events flicker / disappear then return (note 7)

**Problem:** Calendar events on home intermittently vanish and reappear.

**Root cause:** `getDayAgenda()` returns `[]` on *any* error and never throws
(`day-agenda.ts:57-60`); the backend builds a **fresh `EKEventStore`** per call
(`eventkit.rs:216,269`) with no persistent cache, so a cold/warming EventKit read transiently
returns empty. `DayAgenda.tsx` already has anti-flicker (keep prior calendar rows when a fresh
read loses all of them, `:666-697`), but gaps remain: the **first** load has no prior state to
fall back on, and the **separate, unguarded** home count loader (`app/page.tsx:216-240`) calls
`getDayAgenda()` independently with no anti-flicker.

**Approach:** Extend the existing anti-flicker to the uncovered paths — cache last-good agenda
items (sessionStorage or a shared store) so even the first paint after a transient failure shows
the previous list; route the home count loader through the same guarded source; and distinguish
"empty because no events" from "empty because the read failed" (return a Result/typed error from
`getDayAgenda()` instead of swallowing to `[]`). Optionally retain the last successful EventKit
read in the backend to bridge cold reads.

**Files:** `frontend/src/lib/day-agenda.ts:53-60`,
`frontend/src/components/Calendar/DayAgenda.tsx:661-754`,
`frontend/src/app/page.tsx:216-240`,
`frontend/src-tauri/src/calendar/eventkit.rs:184-330`,
`frontend/src-tauri/src/calendar/day_agenda.rs`.

No dismiss/ignore mechanism exists for events today (the agenda applies only phase/recording

## WS6 — Summary & titling (P2)

> Owner: llm-pipeline-engineer + rust-core-engineer.

### WS6.1 — P2: auto-title ad-hoc calls on summarize; never overwrite a manual edit (note 11)

**Problem:** Summarizing a call that still has a generic date-time title doesn't change the
title. Ad-hoc (non-calendar) meetings should be **auto-titled** from the summary; but if the user
**manually edited** the title, it must **not** be overwritten.

**Root cause:** The only "don't overwrite" guard today is `title_is_authoritative =
meeting has a non-empty calendar_event_id` (`service.rs:660-670`, mirrored at
`useSummaryGeneration.ts:284-288`). This conflates two distinct cases and provides **no
"manually named" flag**: a manual rename on a non-calendar meeting can still be clobbered by the
next summary, while the user reports the opposite symptom (ad-hoc date-time titles *not* getting
renamed) — so the rename path is either not firing or `extract_meeting_name_from_markdown`
(`processor.rs:457`) is returning empty. Both halves of the desired behavior are missing.

**Approach:**
- Add a persisted **`title_manually_set`** flag on the meeting row (migration). Set it true when
  the user commits a title edit (`api_save_meeting_title`); the frontend already tracks
  `isTitleDirty` (`useMeetingData.ts:39-42`) but doesn't persist intent.
- Change the rename guard from "has `calendar_event_id`" to "**`calendar_event_id` set OR
  `title_manually_set`**". So: ad-hoc + auto-generated date-time title → **rename** on summarize;
  ad-hoc + manually renamed → **keep**; calendar meeting → keep (unchanged).
- Verify the ad-hoc rename actually fires end-to-end (the user's symptom): confirm
  `extract_meeting_name_from_markdown` returns the H1 and `update_meeting_name` runs for a
  non-calendar meeting; add a test.

**Files:** new migration under `frontend/src-tauri/migrations/` (`title_manually_set`),
`frontend/src-tauri/src/summary/service.rs:660-686`,
`frontend/src-tauri/src/summary/processor.rs:457`,
`frontend/src/hooks/useSummaryGeneration.ts:284-288`,

## Risks / open questions

- **WS2.2 (DL expansion) is fundamentally limited.** EventKit returns a distribution list as one
  participant and does not expand server-side groups; there is no local roster to expand from.
  True expansion needs Contacts (only for locally defined groups) or manual entry. **Decision
  needed:** accept "label + manual add" for 1.2, or commit to a Contacts-permission integration
  as a follow-up spec?
- **WS2.1 vs WS6.7 net.** The refuse-to-merge safety net is correct for *consecutive* sessions
  but must not fire for the *first* save of a calendar meeting. Verify the id reaching the save is
  the pre-created calendar row; the real fix is making the calendar row the single durable target,
  not weakening the net.
- **WS4.1 is a runtime triage, not a known-line fix.** It needs a real-meeting instrumentation
  pass first; the fix depends on what sherpa reports (`total<=0` vs coarse callback vs silent
  channel). Budget for diagnosis.
- **WS7.1 adds a new backend audio path** (per-chunk FFT + a new event) on the hot recording
  loop — must be throttled like `recording-level` (80 ms) and cheap enough not to affect capture.
  Decide band count and exact Hz cutoffs (proposed ~80 Hz–4 kHz, log-spaced).
- **WS5.2 recurring events.** Dismiss-occurrence vs dismiss-series; default to occurrence id but
  recurring occurrences can share an EventKit id (per the 0019 WS6.3 caveat) — verify the id is
  occurrence-unique before relying on it as the dismissal key.
- **WS8.1 placement** is a UX call (Summary tab vs restored right column) — confirm with owner.
