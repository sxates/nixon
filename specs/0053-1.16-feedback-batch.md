# 0053 — 1.16 feedback batch: constrained extraction output, multi-threaded diarization, auto summary structure

- **Status:** Implemented (pending owner smoke) — shipped v1.17.0
- **Owner agent(s):** llm-pipeline-engineer (WS1, WS3) + audio-engineer (WS2) + rust-core-engineer (WS1 provider plumbing, WS3 persistence) + frontend-engineer (WS3 picker)
- **Roadmap phase:** Feedback batch (1.16)

## Context / Problem

Three owner-reported items from real 1.16 use. All three are root-caused below; none is
speculative.

### 1. Action-item extraction intermittently fails to produce parseable output

Reported error: *"Action-item extraction failed: Model returned unparseable action-item output
twice; giving up on this run: model reply contains no JSON array opening bracket"*.

> **CORRECTED DURING IMPLEMENTATION (2026-08-20).** This section originally claimed
> `action_item_extractions` holds 0 rows, "so every run since specs/0034 shipped has failed".
> That read the **production** database — which has 2 meetings and zero summaries, so extraction
> never ran there at all. The **dev** database, where the owner actually dogfoods, has 29
> meetings, 6 summaries and **3 successful extractions**. The failures are intermittent, matching
> the owner's own wording ("getting *some* processing errors"). The most recent extraction ran on
> `ollama/gemma4:26b`, not the built-in model, so the reported failure may not involve BuiltInAI.
>
> Attempts to reproduce the failure on the three real summaries that lack an extraction row, 3
> runs each on `qwen3.5:4b` under both the old and new sampling profiles, parsed **9/9 both ways**.
> The root cause of the owner's specific failure is therefore **not established**. What follows is
> a real defect found while investigating, and fixing it is a genuine robustness improvement — but
> it is not proven to be the cause of the reported error.

The install runs `provider = builtin-ai`, `model = qwen3.5:4b` (`settings` row 1).

Two independent causes compound:

**(a) The local provider silently discards the call site's sampling intent.**
`summary::llm_client::generate_summary` short-circuits BuiltInAI at
`frontend/src-tauri/src/summary/llm_client.rs:234`, returning
`summary_engine::generate_with_builtin(...)` **before** `max_tokens`, `temperature`, or `top_p`
are ever read. Those three parameters are accepted by the signature and dropped on the floor for
this provider.

`action_items/extractor.rs:496` passes `Some(0.0)` temperature with the comment "deterministic
extraction (specs/0034)". It has never taken effect. What the sidecar actually applies is the
model's **summary** sampling profile (`summary_engine/models.rs:56`,
`SamplingParams::qwen35_summary`): `temperature 0.5, top_k 20, top_p 0.8, presence_penalty 0.3,
frequency_penalty 0.0, repeat_penalty 1.05, penalty_last_n 256`.

`presence_penalty: 0.3` is the direct antagonist of a JSON array. The required output repeats
`{`, `"description"`, `"assignee"`, `"due"`, `}` on **every** element; a presence penalty lowers
the logit of exactly those tokens after their first occurrence. The pressure to abandon the
format compounds with array length — precisely backwards for this task.

**(b) Nothing constrains the output; the parser is purely post-hoc.**
`parse_candidates` (`extractor.rs:394`) does the right defensive things — strip reasoning tags via
`clean_llm_markdown_output`, prefer an inner fenced block, slice first `[` … last `]`, strict
serde — but it can only recover structure that is *present*. When the reply contains no `[` at
all it raises `"model reply contains no JSON array opening bracket"`, the reported error. The
single retry (`extract_with_llm`, `extractor.rs:451`) appends `RETRY_REMINDER` and re-rolls **the
same sampling profile**, so it fails the same way — producing the observed *"twice; giving up on
this run"*.

**Ruling out length as a cause.** A reply truncated at `max_tokens` loses its *closing* `]`, not
its opening `[`, and would surface as `"...no JSON array closing bracket"`. "No opening bracket"
means the model emitted prose or a bare object — a **format** failure, not a length failure.
`models::DEFAULT_MAX_TOKENS = 4096` is therefore not implicated, and is recorded here only to
close the question.

**The capability appeared to be in the tree — it is not usable.** `llama-cpp-2 = "=0.1.146"`
exposes `LlamaSampler::grammar`, and this batch originally built GBNF-constrained decoding on it.

> **REMOVED DURING IMPLEMENTATION (2026-08-20), verified against the real model.**
> `LlamaSampler::grammar` **aborts the process**: `GGML_ASSERT(!stacks.empty()) failed` at
> `llama-grammar.cpp:940` → SIGABRT. This is not a defect in our grammar — llama.cpp's own
> bundled `json.gbnf`, `json_arr.gbnf`, `arithmetic.gbnf`, `chess.gbnf` and even a trivial
> `root ::= "yes"` crash identically through this integration. Shipping it would have killed the
> sidecar on every constrained call, taking summarization down with it.
>
> A second defect surfaced on the way: llama.cpp's GBNF parser **ends a rule at the newline**, so
> the multi-line `item` rule never parsed (`error parsing grammar: expecting name`). A failed
> parse does not surface as an error — it silently yields empty output. Both defects were missed
> by the unit tests, which only asserted the grammar string *contained* substrings and never fed
> it to a parser.
>
> The `grammar` field remains on `GenerationOptions` and in the sidecar protocol, documented and
> never set, so it becomes usable if `llama-cpp-2` is upgraded and re-tested.

### 2. Speaker identification is single-threaded by a hardcoded constant in a dependency

`sherpa-rs 0.6.8`'s `src/diarize.rs` hardcodes `num_threads: 1` on **both** ONNX model configs it
builds — `SherpaOnnxSpeakerEmbeddingExtractorConfig` and
`SherpaOnnxOfflineSpeakerSegmentationModelConfig` — with no way to override from
`DiarizeConfig`, whose public fields are only `num_clusters`, `threshold`, `min_duration_on`,
`min_duration_off`, `provider`, `debug`.

Vinyl already knows this. `diarization/accel.rs:58` states it outright: *"sherpa-rs hardcodes the
diarizer's threads to 1, but the standalone `EmbeddingExtractor` does expose `num_threads`, so we
raise it."* The workaround therefore covers only the **per-cluster re-embed** pass. The main pass
— pyannote segmentation plus CAM++ embedding across the entire recording inside one
`Diarize::compute` call (`diarization/sherpa.rs:508`) — runs on a single core.

There is no acceleration of any other kind either: `accel.rs:44` documents that the CoreML
execution provider is no longer the default because its init throws a C++ exception under the
production hardened runtime that escapes `Diarize::new` as `terminate()`/`abort()` — a hard crash
`build_with_provider_fallback` cannot intercept. So the pass is CPU, one thread.

Owner-reported cost on long calls: **15–45 minutes**.

### 3. Summary structure is decided before the model has seen the meeting

`processor.rs:984` builds the final synthesis prompt from `template.to_markdown_structure()` and
`template.to_section_instructions()`, both derived from a `Template` resolved by id at
`service.rs:582` — before generation begins. Every meeting is therefore forced into one of six
author-time layouts.

The default, `standard_meeting.json`, is four fixed sections (Summary, Key Decisions, Action
Items, Discussion Highlights) and mandates that Action Items render as a **table** with
`| **Owner** | Task | Due | Reference Transcript Segment | Segment Time stamp |`. That shape is
imposed whether or not the meeting produced any commitments, and the transcript-reference columns
are noisy for most content. A one-on-one, a design debate, an incident review, and a status sync
all come out shaped like a status sync.

`api_suggest_template_for_title` (`summary/template_commands.rs:404`) exists but only donates a
prior same-title meeting's choice via `MeetingsRepository::suggest_template_for_title`. It reads
nothing from the meeting's content.

## Goals

- Action-item extraction produces parseable output on the built-in local model. (Originally
  "structurally rather than by persuasion" via a grammar — see the correction above; delivered as
  deterministic sampling that actually reaches the sidecar, plus provider-native JSON mode.)
- A call site's sampling intent (`temperature`, `max_tokens`) reaches **every** provider,
  including BuiltInAI.
- Speaker identification uses the machine's cores. Target ≥2.5x wall-clock on a real long
  recording, with diarization accuracy held at the existing DER baseline.
- Summaries are structured from the meeting's own content by default, while the six built-in
  templates remain available and unchanged for users who want a fixed shape.
- A meeting with no commitments does not pay for an action-item extraction call, and says so
  visibly rather than skipping in silence.

## Non-goals

- **Block-parallel diarization.** Splitting long audio into concurrently-diarized blocks with
  global re-clustering would beat threading on very long calls, but it perturbs clustering and
  puts the hard-won ~8% macro DER baseline (specs/0043, 0050) at risk. Owner decision
  (2026-08-20): ship threading first, iterate if still too slow. Named here as the expected
  follow-up, not smuggled into this batch.
- **Re-enabling CoreML/ANE for diarization.** The hardened-runtime abort (`accel.rs:44`) is a
  separate investigation with a crash, not a slowdown, as its failure mode.
- **Claude structured output.** No JSON mode on `/v1/messages` without tool-forcing; Claude is a
  large model and is not the failing case. It keeps the prompt + defensive parse.
- **Replacing or removing the six built-in templates**, or changing their JSON.
- **Date parsing for `due`.** Still a verbatim hint (specs/0034 v1 decision, unchanged).
- **A user-facing thread-count setting.** `VINYL_DIARIZATION_THREADS` remains the seam.

## Approach

Three independent workstreams, sequenced W1 → W3 (W3 reuses W1's grammar machinery) with W2
parallel to both.

**W1** fixes the extraction failure at the layer where it is actually decidable. Prompt-level
pleading has already been tried (`RETRY_REMINDER`, the "Return ONLY the JSON array" closing line,
the `SYSTEM_PROMPT_HEADER` contract) and demonstrably does not hold a 4B model. A GBNF grammar
makes non-JSON unrepresentable in the sampler, so the failure mode disappears rather than becomes
rarer. Fixing the dropped sampling parameters is necessary independently — the penalties are
actively steering the model wrong, and a silently-ignored `temperature: 0.0` is a bug regardless
of this batch.

**W2** takes the narrowest possible path to the cores: bind `sherpa-rs-sys` directly for the
diarizer construction only, so `num_threads` becomes settable, and leave everything else —
clustering, tuning, consolidation, the progress callback contract — byte-identical. `sherpa-rs`
stays a dependency for the standalone `EmbeddingExtractor` that `identity.rs` uses. Rejected
alternatives: vendoring a patched `sherpa-rs` fork (a whole crate to carry for one integer), and
upstreaming a PR (right thing long-term, wrong latency for this batch — worth doing separately).

**W3** keeps the entire proven summarization pipeline and changes only *where the section list
comes from*. A cheap grammar-constrained call derives a `Template` at runtime from the reduced
meeting content; every downstream stage — chunking, caching, notes grounding, speaker attribution,
role weighting, length guidance — is untouched. Rejected alternatives: a fully free-form
single-pass prompt (worst results on exactly the small local models this install runs), and a
router over the six existing templates (still six fixed layouts, so it does not answer the
request).

## Design

### W1 — Constrained structured output

**`llama-helper/src/grammar.rs`** (new). `main.rs` is at 748/800 lines against the 0042 ratchet,
so grammar support lands as its own module, not inline.

- `Request::Generate` gains `grammar: Option<String>` (GBNF source).
- When `Some`, `LlamaSampler::grammar(&model, &gbnf, "root")` is prepended to the sampler chain so
  it masks logits **before** temperature and the penalty samplers run. Order is load-bearing and
  gets a test.
- When `None`, the chain is byte-identical to today's (`main.rs:413`). Existing callers are
  unaffected.

**`frontend/src-tauri/src/summary/summary_engine/options.rs`** (new).

- `GenerationOptions { max_tokens: Option<i32>, temperature: Option<f32>, grammar: Option<String>,
  neutral_penalties: bool }`, with `Default` reproducing today's behaviour exactly.
- `generate_with_builtin` takes `&GenerationOptions` and layers it over
  `model_def.sampling.sanitize_for_llama_helper()` instead of using that profile unconditionally
  (`summary_engine/client.rs:179`).
- `neutral_penalties` sets `presence_penalty 0.0`, `frequency_penalty 0.0`, `repeat_penalty 1.0`
  — required for any repeating structured format.

**`summary/llm_client.rs`.**

- `generate_summary` gains a `GenerationOptions`-shaped parameter and **forwards it** on the
  BuiltInAI branch (`llm_client.rs:234`) instead of discarding `max_tokens`/`temperature`.
- `ChatRequest` gains `response_format: Option<serde_json::Value>`, serialized only when `Some`,
  set to `{"type":"json_object"}` when the call site requests JSON. Applies to Ollama (whose
  `/v1/chat/completions` honors it) and every OpenAI-compatible provider. **Never** emitted for
  Claude — asserted in a test, since `ClaudeRequest` is a separate struct and a stray field would
  be a 400.

**`frontend/src-tauri/src/action_items/grammar.rs`** (new). The GBNF for
`[{description, assignee, due}, ...]`: an array (possibly empty) of objects with exactly those
three keys, `description` a string, `assignee` and `due` each string-or-null. It is the grammar
form of the `ActionItemCandidate` serde contract, and a test asserts a round-trip against the
existing `CLEAN_ARRAY` fixture (`extractor.rs:916`).

**`action_items/extractor.rs`.** `extract_candidates` requests `temperature 0.0`,
`neutral_penalties: true`, and the grammar (BuiltInAI) / `response_format` (OpenAI-compatible).
The defensive `parse_candidates` chain **stays** as the backstop for providers that honor neither.
The `extract_with_llm` retry stays. Net effect: the belt is new, the braces are unchanged.

### W2 — Multi-threaded diarization

**`Cargo.toml`.** Add `sherpa-rs-sys = { version = "0.6.8", default-features = false, features =
["download-binaries"] }` as a direct dependency. Cargo already resolves that exact version
transitively (`Cargo.lock:5690`), so this unifies to one copy — no second native-library download
and no change to the build.

**`frontend/src-tauri/src/diarization/sherpa_sys.rs`** (new, ~120 lines). A minimal safe wrapper
mirroring `sherpa_rs::diarize::Diarize`'s call sequence exactly:

- `SherpaOnnxCreateOfflineSpeakerDiarization` with `num_threads` set from
  `accel::diarizer_threads()` on **both** the segmentation and embedding configs (the only
  substantive difference from upstream), and a `Drop` impl calling the destroy entry point.
- `SherpaOnnxOfflineSpeakerDiarizationProcessWithCallback`, returning the same
  `Segment { start, end, speaker }` shape and preserving the progress-callback contract
  (`(processed, total) -> i32`, `0` = continue).
- The `NO_SEGMENTS_MARKER` empty-result error text is preserved verbatim, because `sherpa.rs:520`
  matches on it to distinguish "no speech" from a genuine model failure.

All new `unsafe` is confined to this one file.

**`diarization/accel.rs`.** Add `diarizer_threads()` beside the existing `embedding_threads()`:
same `VINYL_DIARIZATION_THREADS` override, same `[MIN_THREADS, MAX_EMBED_THREADS]` = [1, 8] clamp,
same `available_parallelism()` default. The 8 cap stays — ONNX intra-op parallelism yields
diminishing returns past a handful of cores on these small models, and the pass must not starve
the rest of the app. The module doc's "sherpa-rs hardcodes the diarizer's threads to 1" note is
updated to record that we no longer go through sherpa-rs for the diarizer.

**`diarization/sherpa.rs`.** Swap `sherpa_rs::diarize::{Diarize, DiarizeConfig}` for the new
wrapper. Everything else — `DiarizeTuning`, `SpeakerCount`, `build_clusters`,
`merge_clusters_to_at_most`, `consolidate_clusters`, the over-cluster guardrail, the silence
pre-check — is untouched. The FFI progress-callback bridge currently inline at `sherpa.rs:456-505`
(the `SendPtr` transmute block) moves into `sherpa_sys.rs`, where it belongs next to the call it
guards; that is what makes `sherpa.rs` **shrink** rather than grow past its ratchet entry.

`sherpa-rs` remains a dependency — `identity.rs` uses its standalone `EmbeddingExtractor`.

### W3 — Auto summary structure

**Reserved template id `auto`.** Becomes `DEFAULT_TEMPLATE_ID` (`useTemplates.ts:7`) and the
backend fallback when `meetings.template_id IS NULL`. Meetings with an explicitly persisted
`template_id` keep it — no migration of existing choices, no change to any existing summary.
`templates/loader.rs` reserves the id so it can neither be created nor deleted as a user template.

**`frontend/src-tauri/src/summary/outline.rs`** (new). `derive_outline(...) -> Result<Outline>`:

```rust
struct Outline {
    sections: Vec<OutlineSection>,
    has_commitments: bool,
}

struct OutlineSection {
    // The existing TemplateSection fields, verbatim:
    title: String, instruction: String, format: String, item_format: Option<String>,
    // Validation-only. NOT carried into Template — the rendered prompt is unchanged.
    role: Option<SectionRole>,   // "overview" | "commitments" | null
}
```

`role` exists so validation identifies the overview and commitments sections **structurally**
rather than by pattern-matching titles — the model is free to title the commitments section
"Next Steps", "Follow-ups", "Who's doing what", or anything else that fits the meeting, which is
the entire point of Auto. The grammar makes `role` a closed enum, so it cannot arrive misspelled.
It is dropped when converting `Vec<OutlineSection>` → `Template`, so the downstream prompt is
byte-identical in shape to a fixed template's.

Placement: `processor.rs`, immediately **after** the map/reduce collapse has produced
`content_to_summarize` and **before** `template.to_markdown_structure()` (`processor.rs:984`). On a long meeting this
reads the already-reduced text rather than the transcript, so it is the cheapest call in the
pipeline and adds no chunking work.

The call is grammar-constrained via W1. Constraints are enforced in **Rust**, not merely requested
in the prompt:

| Constraint | Why |
|---|---|
| 3–6 sections | Bounds output; a 4B model degrades past ~6 section instructions |
| Section 1 is a prose overview (`format: "paragraph"`) | Every consumer — meeting list, search snippet, prep brief — expects a lead paragraph |
| A commitments/next-steps section is **required** when `has_commitments` | `action_items/extractor.rs` reads the **summary** as its primary source. An outline that drops this section would silently break action items. Non-negotiable. |
| `format` ∈ {`paragraph`, `list`, `string`} | `to_section_instructions` only understands these three |
| `item_format` (tables) only when content is genuinely tabular | Retires the forced Action Items table with its `Reference Transcript Segment` / `Segment Time stamp` columns |
| Titles rejected if they carry `<...>` / `[...]` | Template-echo guard, reusing the `is_valid_meeting_title` check (`processor.rs:724`) |

**Fallback.** Any failure — transport, parse, or validation — falls back to `standard_meeting`,
logs at `warn`, and generates normally. Auto never blocks or degrades a summary.

**Skip extraction when there are no commitments** (owner request, 2026-08-20). The outline pass
already reads the whole reduced meeting, so `has_commitments` is free. The background extraction
spawn at `service.rs:789` skips the LLM call when **all** of:

1. the meeting used Auto, **and**
2. the persisted outline says `has_commitments == false`, **and**
3. the outline contains no next-steps section, **and**
4. the meeting has **no user notes**.

Condition 4 matters: `extract_candidates` takes the owner's notes as a **second** source
(specs/0034 recall mitigation), and a commitment can live only in the notes. Skipping on a
notes-bearing meeting would regress that.

The manual "Scan again" path (`action_items/commands.rs:332`) is **never** gated — an explicit
user request always runs.

The skip is **recorded, not silent**: a `TaskKind::ActionItems` outcome goes to the specs/0052
activity registry with the reason "no commitments found in this meeting", so it appears in the
sidebar activity list. specs/0052's own lesson was that silent no-op exits are indistinguishable
from breakage. No ledger row is written, so a later manual scan still runs for real — worst case
on a false negative is a visible, one-click-recoverable miss, not silent data loss.

### Data model

New migration under `frontend/src-tauri/migrations/`:

```sql
CREATE TABLE meeting_summary_outlines (
    meeting_id      TEXT PRIMARY KEY REFERENCES meetings(id) ON DELETE CASCADE,
    outline_json    TEXT NOT NULL,     -- serialized Outline (sections + has_commitments)
    has_commitments INTEGER NOT NULL,  -- denormalized for the extraction gate
    derived_at      TEXT NOT NULL
);
```

**Caching.** `template_cache_fingerprint` (`service.rs:229`) fingerprints the *rendered* template,
which for Auto is not known until mid-generation. For `template_id = 'auto'` the fingerprint is
taken from the **persisted** outline. First run: derive → persist → generate (cache miss, which is
correct — nothing was cached). Regeneration and re-render reuse the stored outline, so the shape
is stable across runs and the summary cache behaves exactly as it does for a fixed template. A
"Re-think structure" action clears the row and re-derives.

### Tauri IPC

- `api_clear_summary_outline(meeting_id)` — the "Re-think structure" action. Registered in
  `registry.rs` per specs/0042.
- No new events. Auto reuses the existing summary progress/completion events unchanged.

### UI

- Template picker gains **"Auto (recommended)"** pinned at the top, described as *"Structure
  chosen from the meeting's content."* The six built-in entries are unchanged and unreordered
  below it.
- `shouldConfirmTemplateChange` (`useTemplates.ts`) already handles confirm-before-regenerate;
  Auto is just another id to it.
- "Re-think structure" appears in the summary panel's existing regenerate affordance only when the

## Acceptance criteria

1. **Extraction succeeds on the built-in model.** After a summary on `builtin-ai`/`qwen3.5:4b`,
   `action_item_extractions` has ≥1 row. The table is empty today, so this is unambiguous.
2. **Sampling intent reaches the sidecar.** A test asserts `generate_with_builtin` receives
   `temperature 0.0` and neutral penalties when extraction asks for them — the assertion that
   would have caught this bug at `llm_client.rs:234`.
3. **Grammar output is structurally valid.** With the grammar active, 20 consecutive extraction
   calls over stored summaries yield 20 parseable replies (`parse_candidates` never errors).
4. **Diarization speed:** ≥2.5x wall-clock. **MEASURED 2026-08-20: 3.29x** (510s → 155s for the
   full `eval_regression_gate` across all three `zoom-samples` recordings, same binary,
   `VINYL_DIARIZATION_THREADS=1` vs the default 8). PASSES.
5. **Diarization accuracy:** macro DER within **0.5 points absolute** of baseline.
   **MEASURED 2026-08-20: bit-identical, zero drift.** 1-thread vs 8-thread per-file DER —
   `long-1-1` 5.73% / 5.73%, `long-many-speakers` 8.39% / 8.39%, `short-4-speakers` 10.10% /
   10.10%. All below their pinned maxima (9.00 / 12.00 / 14.00). PASSES.
6. **Auto is default and content-shaped.** A new meeting summarizes on Auto; two meetings of
   genuinely different character produce genuinely different section lists; neither contains an
   unfilled `<...>`/`[...]` token.
7. **Auto never blocks a summary.** With `derive_outline` forced to fail, the summary still
   generates on `standard_meeting` and logs the fallback.
8. **Existing template choices are untouched.** A meeting with a persisted `template_id` produces
   a byte-identical summary to pre-change, given the same input and model.
9. **The extraction skip is correct and visible.** A commitment-free, notes-free Auto meeting
   makes no extraction call and shows a skip outcome with its reason in the sidebar activity list.
   The same meeting **with** notes does run extraction. "Scan again" always runs.
10. **DoD (`/CLAUDE.md`):** `cargo check`/`clippy`/`test` clean; `pnpm lint`/`test` clean;
    `scripts/check-file-size.sh` passes; app launches via `./clean_run.sh`; record → live
    transcript → summary smoke path works.

## Risks / open questions

- **Threading lands at 5–15 min, not 2.** A 3x win on a 15–45 minute pass is real but not fast.
  Owner has accepted this explicitly and chosen to iterate. Criterion 4's 2.5x floor is what keeps
  a disappointing result from shipping unremarked.
- **New `unsafe` FFI.** `sherpa_sys.rs` is hand-written bindings where a mistake is a crash or
  worse. Mitigation: mirror sherpa-rs's proven sequence exactly, confine all `unsafe` to one file,
  change only `num_threads`, keep the CPU provider default.
- **Intra-op threading changes float reduction order.** Results may differ in the last bits and,
  through clustering, could nudge speaker boundaries. Criterion 5 is the gate; if DER moves more
  than 0.5 points, drop the thread count rather than accept the regression.
- **`has_commitments` is a 4B model's judgement.** A false negative costs the user their action
  items. Mitigated by the four-condition gate (notes-bearing meetings never skip), by recording
  the skip visibly, and by writing no ledger row so "Scan again" always re-runs.
- **Auto adds one LLM call per summary.** It runs on the reduced text, so it is the cheapest call
  in the pipeline — but on a local model every call has a floor. Measure it; if it proves material
  on short meetings, skip the outline pass below a transcript-size threshold and use
  `standard_meeting`.
- **Grammar-constrained decoding can degrade content quality** by forcing structure the model
  would otherwise decline to produce (e.g. inventing an action item to fill a non-empty array).
  The grammar permits `[]`, and the specs/0034 zero-candidate quarantine
  (`skip_zero_candidate_deletes`) already protects against an empty result deleting pristine rows.
- **Open:** should Auto also apply to the specs/0036 pre-call prep brief, which has its own
  prompt? Out of scope here; revisit once Auto has run on real meetings.
