## Context / Problem

A full day of real-world testing on the **1.2 dev build** (2026-07-01) produced a 20-item
feedback batch. Every item below is grounded in the *current* tree (branch
`audit/robustness-hardening`); file:line anchors were verified at spec-authoring time.

Headline findings from the investigation:

1. **A 0028 security hardening regression broke Zoom launch.** `open_external_url` now
   allows only `http|https|mailto` (`api/api.rs:1302-1331`), but "Join & Record" opens the
   `zoommtg://` deep link — the open silently fails (`calendar.ts:85-87` swallows the error),
   so Zoom never launches. One-line-class fix, ships first.
2. **One race explains both calendar regressions** (title + attendees, items 3/10): the
   pending-join stash in `joinAndRecord` happens *after* an awaited DB create, while opening
   Zoom trips the Zoom monitor's own "Record this meeting?" toast during the 3-second delay.
   Whichever start path wins without the pending-join mints a date-stamped row with **no
   `calendar_event_id`** — which also disables attendee seeding *and* the 0024 WS2.1 backend
   dedupe net (they both key off the calendar link).
3. **One missing guard explains three diarization symptoms** (items 8/17): there is **no
   per-meeting "already running" guard** for diarization, and the UI's in-progress state is
   component-local — navigate away and back and the button re-enables. A second concurrent
   run interleaves its 0→100 progress with the first (the oscillating 76→28→85→35), and each
   completing run `DELETE FROM speakers` — wiping manual renames.
4. **The notes cross-contamination is an id-binding bug**: the record screen's notepad binds
   to the mutable *viewed-meeting* global (`currentMeeting.id`) instead of
   `activeRecordingMeetingId`, so viewing an old meeting mid-recording silently retargets the
   live notepad.
5. **The spectrometer's only data source is the VAD-gated transcription queue** — it was
   always dead during silence, and the 0028 pipeline changes (per-call resampler allocation,
   bounded drop-newest queues) made total starvation easy. The fix is to emit from the raw
   mixed-window path.

**What worked (item 7):** Zoom meeting end was detected and the recording stopped cleanly —
the 0024 WS1.1 full-stop path is holding. Item 8's oscillation aside, diarization progress
is no longer stuck at 0% (0024 WS4.1 held too).

## Goals

- "Join & Record" launches Zoom again, and Vinyl's own auto-detect prompt can never race
  the join flow into a mistitled, attendee-less meeting.
- A meeting started from a calendar event is **one** row carrying the event title,
  `calendar_event_id`, seeded attendees, transcript, and recording — under every start path.
- Notes always save to the meeting whose content is on screen; pasted text takes on our
  styling.
- The live transcript is scannable: appends never move the viewport unless the user is
  already at the bottom.
- The spectrometer animates whenever audio is flowing, independent of VAD/transcription.
- Diarization: one run at a time per meeting, monotonic progress, status that survives
  navigation (and shows on the home list), renames that survive re-runs, and a speaker
  count informed by the participant roster.
- The user's own voice ("you") stays attributed in the final transcript; live per-speaker
  detection stops burning CPU for labels we throw away.
- Recording is visibly indicated on home/all-meetings; search is clickable; hide/unhide is
  immediate and truthful; notifications wear the Vinyl icon.
- Opt-in lifecycle controls: auto-summarize on call end (verified & surfaced), audio
  retention, and record-only mode with deferred transcription.

## Non-goals

- Rewriting the meetily capture/mix/VAD pipeline (kept per `/CLAUDE.md`). WS1.2 diagnoses
  tap↔Zoom contention; it does not redesign capture.
- Per-track (dual) STT — WS3.4 preserves the mic/system distinction via a channel tag and
  mic-track alignment, not by transcribing two streams.
- Replacing the diarization model or clustering algorithm (WS3.3 tunes sizing/caps only).
- Editable template *content* — WS4.3 needs only the `meetings.template_id` persistence
  slice of spec 0020, not the full editable-templates feature.
- Cloud/calendar-provider integrations beyond what EventKit already gives us.

## WS1 — Zoom launch & recording interplay (P0/P1)

> Owner: rust-core-engineer + audio-engineer + frontend-engineer.

### WS1.1 — P0: "Join & Record" never launches Zoom (note 5, first half)

**Problem:** Clicking "Join and Record" starts the recording but Zoom never opens.

**Root cause (confirmed):** `openZoomMeeting` (`frontend/src/lib/calendar.ts:210-213`)
prefers the `zoommtg://` deep link and routes it through
`invoke('open_external_url')` (`calendar.ts:82-88`). The 0028 hardening restricted that
command to `http | https | mailto` (`frontend/src-tauri/src/api/api.rs:1302-1331`, scheme
check at `:1313`), so the deep link returns `Err` — which `openMeetingUrl` swallows with a
`console.warn` (`calendar.ts:85-87`). The allowlist (0028) post-dates the deep-link feature
(0008 P3); only non-standard links that fall back to plain `https` still work.

**Approach:** Add `zoommtg` (and `zoomus`) to the allowlist — or add a dedicated,
strictly-validated `open_zoom_deeplink` command so the general allowlist stays tight.
Stop swallowing the failure: if the deep link is rejected/fails, fall back to opening the
`https` URL and surface a toast if both fail. Add a regression test on the scheme check.

**Files:** `frontend/src-tauri/src/api/api.rs:1302-1331`,
`frontend/src/lib/calendar.ts:82-88,210-213`.

### WS1.2 — P1: an active recording hangs Zoom's join (note 5, second half)

**Problem:** With a recording already running, launching Zoom hangs until the recording is
stopped. The user wants start-recording-then-join to be a durable path.

**Root cause (strong hypothesis, needs runtime confirmation):** `CoreAudioCapture::new`
creates a **global mono process tap excluding no processes** plus a private aggregate device
with `tap_auto_start = true` (`frontend/src-tauri/src/audio/capture/core_audio.rs:95,
128-149`). When Zoom initializes its audio engine while that tap is live, both contend in
`coreaudiod` and Zoom stalls; dropping the tap (`capture/system.rs:136-148`,
`core_audio.rs:372-377`) unblocks it. This collision is already documented — the
`JOIN_AND_RECORD_DELAY_MS = 3000` Zoom-first ordering exists precisely because starting the
tap during Zoom audio init "reliably hangs the Zoom client" (`calendar.ts:161-178`).

**Approach:** Diagnose on a real machine before committing to a fix:
1. Reproduce with logging: tap up → launch Zoom → capture `coreaudiod`/Zoom behavior.
2. Evaluate mitigations in order of preference: **(a)** briefly pause/tear down and rebuild
   the tap when the Zoom monitor sees Zoom's audio host processes appear (`zoom/monitor.rs`
   already watches `cpthost`/`aomhost`), letting Zoom's engine initialize cleanly, then
   re-arm; **(b)** scope the tap (exclude Zoom's processes at creation and re-create the tap
   including them once Zoom is stable); **(c)** if neither is workable, keep Zoom-first
   ordering as the supported path and make the UX honest (disable/queue "record now" while
   Zoom is mid-launch).
3. Whatever lands, keep the WS2.1 pending-join intact across the pause/rebuild.

**Files:** `frontend/src-tauri/src/audio/capture/core_audio.rs:95,128-149`,
`frontend/src-tauri/src/audio/capture/system.rs:136-148`,
`frontend/src-tauri/src/zoom/monitor.rs:135-197`, `frontend/src/lib/calendar.ts:161-180`.

### WS1.3 — P1: "Zoom meeting detected" banner persists after recording starts (note 16)

**Problem:** The "Record this meeting?" prompt lingers after the user starts a recording
some other way.

**Root cause (confirmed):** The prompt is a persistent sonner toast
(`DETECTED_TOAST_ID`, `duration: Infinity`, `ZoomAutoDetect.tsx:120-141`) dismissed only by
its own Record/Ignore buttons or `zoom-meeting-ended`. `isRecording` is in scope
(`ZoomAutoDetect.tsx:66`) but nothing watches it.

**Approach:** Dismiss the toast (and clear `pendingUnpromptedRef`) whenever a recording
begins by any path — effect on `isRecording` or a `safeListen('recording-started', …)`
(backend emits at `recording_commands.rs:501,682`). This also closes one arm of the WS2.1
race (the toast can no longer offer a competing start while a Join-&-Record is armed —
see WS2.1's suppression, which goes further).

**Files:** `frontend/src/components/ZoomAutoDetect.tsx:120-146`.

## WS2 — Calendar → meeting identity: the pending-join race (P0)

> Owner: frontend-engineer + rust-core-engineer. Third strike for this symptom (0019
> WS6.3, 0024 WS2.1) — this time the concrete dropped-hand-off race is identified.

### WS2.1 — P0: calendar meetings still mistitled with no participants (notes 3, 10)

**Problem:** A meeting created from a calendar event gets the date-stamp title, an empty
participants list, and attendees are no longer auto-added (regression).

**Root cause (confirmed — one dropped hand-off, both symptoms):** In
`useRecordingStart.ts`, both the title and attendee seeding hang off the pending-join
object: the title falls through to `generateMeetingTitle()` when `pendingJoin` is null
(`useRecordingStart.ts:207,284,380`) and seeding runs **only** inside the `preCreated`
branch (`:87,91-103`). The plain create path (`:113-125`) passes no `calendarEventId`, so:
attendee resolution returns empty (`diarization/commands.rs:576-580`), and the 0024 WS2.1
backend dedupe (`api/api.rs:1069-1085` → `meeting.rs:96-116`
`find_adoptable_calendar_meeting`) never engages — it only fires when the frontend passes
the calendar id.

The concrete race: `joinAndRecord` (`calendar.ts:291-341`) opens Zoom **first** (`:297`),
then *awaits* `api_create_meeting`, and only after the await stashes the pending-join
(`:333-338`) before arming a 3 s `setTimeout(startRecording)` (`:340`). Opening Zoom trips
the backend monitor (`zoom/monitor.rs:184-197` emits `zoom-meeting-detected` whenever not
recording), whose toast lets the user start a **plain** recording during the window.
`useRecordingStart`'s auto-start consumes the (not-yet-set) stash → null → date-stamp row,
and `meetingCreatedRef` (`:75-76`) then blocks any later adoption; the delayed
`handleRecordingToggle` no-ops because recording is already live
(`SidebarProvider.tsx:168`). Three independent consume sites (`useRecordingStart.ts:206,
283,379`) plus other start triggers (tray toggle `layout.tsx:125-137`, sidebar) widen the
window. 0028 did not touch this logic (confirmed) — the race was always there; the toast
just makes it easy to lose.

**Approach:**
- **Stash before anything can race.** Write the pending-join to sessionStorage (and to a
  synchronous in-memory slot on the recording state) *before* opening Zoom and *before* the
  awaited create — with optimistic title/eventId, reconciling the SQLite id when
  `api_create_meeting` returns.
- **Suppress the competing prompt.** `ZoomAutoDetect` checks `peekPendingJoinMeeting()`
  (and the WS1.3 dismissal) so a detected Zoom launch during an armed Join-&-Record either
  stays silent or routes into the *same* pending-join start.
- **One consume path.** Unify the three consume sites; when a pending-join exists, the
  `meetingCreatedRef` early-return must adopt it (or re-title/link the row it created)
  instead of silently discarding it. Never fall through to `generateMeetingTitle()` when a
  calendar link is known.
- **Belt-and-braces backend:** pass `calendarEventId` on *every* create that has one in
  scope so `find_adoptable_calendar_meeting` can do its job; seed attendees whenever a row
  gains a `calendar_event_id` (not only in the `preCreated` branch).

**Files:** `frontend/src/lib/calendar.ts:291-341`,
`frontend/src/hooks/useRecordingStart.ts:75-125,206-207,283-284,379-380`,
`frontend/src/components/ZoomAutoDetect.tsx:88-146`,
`frontend/src/components/Sidebar/SidebarProvider.tsx:168`,
`frontend/src-tauri/src/api/api.rs:1069-1085`,
`frontend/src-tauri/src/diarization/commands.rs:564-626`.

## WS3 — Diarization: concurrency, caps, and channel attribution (P1/P2)

> Owner: audio-engineer + rust-core-engineer + frontend-engineer.

### WS3.1 — P1: concurrent runs — oscillating progress, status lost on navigation (notes 8, 17)

**Problem:** Progress bounces (76→28→85→35); navigating away and back loses the
"identifying…" state; clicking again starts a second run.

**Root cause (confirmed, one cause):** `api_diarize_meeting` has **no "already running"
guard** (`diarization/commands.rs:53-63` → `pipeline.rs:417-427` just spawns). The
frontend's `isRunning`/`progressPct` are component-local `useState`
(`useDiarization.ts:67-69`), torn down on unmount (`:134-139`); the only start guard is that
local state (`:142`). So a remount re-enables the button; a second run's monotonic 0→100
ramp interleaves with the first on the shared `diarization-progress` event, which the hook
applies blindly (`useDiarization.ts:86-95`) — the exact two-ramps signature the user saw.
Within one run the emit is monotonic (`pipeline.rs:392-404`), so this is not a progress-math
bug. The home list (`DayAgenda.tsx:229`) has the same per-instance state.

**Approach:** Add a per-meeting in-flight registry in managed state (backend): second
`api_diarize_meeting` for the same meeting returns "already running" instead of spawning.
Expose `api_diarization_status(meeting_id)` (stage + pct); `useDiarization` rehydrates from
it on mount and keeps rendering live events. Surface the status chip on the meeting lists
(home + all-meetings + meeting-details button). Optionally have the hook ignore
out-of-order pct as defense-in-depth.

**Files:** `frontend/src-tauri/src/diarization/commands.rs:53-63`,
`frontend/src-tauri/src/diarization/pipeline.rs:417-427` (+ a small state map, e.g. in
`diarization/mod.rs` or managed state), `frontend/src/hooks/useDiarization.ts:67-142`,
`frontend/src/components/MeetingDetails/TranscriptButtonGroup.tsx`,
`frontend/src/components/Calendar/DayAgenda.tsx:229`.

### WS3.2 — P1: a completing run wipes manual speaker renames (note 17)

**Problem:** Renames made after run 1 finished were destroyed when a (duplicate) run 2
completed.

**Root cause (confirmed):** `persist` calls `clear_meeting_speakers` — `UPDATE transcripts
SET speaker = NULL` **and `DELETE FROM speakers`** (`speaker.rs:224-237`, its own comment
says "P1 resets them") — then re-upserts generated names ("Speaker N"/"You",
`pipeline.rs:278-289`). Per-*segment* reassignments survive via
`transcript_speaker_overrides` reapply (`pipeline.rs:250-254`); speaker-level *renames* do
not.

**Approach:** Preserve user-set display names across re-runs: before clearing, snapshot
rows whose `display_name` differs from the generated default; after the new upsert, re-apply
by stable key where the key survives, else by embedding-centroid similarity to the prior
speaker (fallback: park the orphaned names in the rename UI as suggestions). WS3.1's guard
prevents the *accidental* second run; this makes deliberate re-runs safe too.

**Files:** `frontend/src-tauri/src/database/repositories/speaker.rs:224-260`,
`frontend/src-tauri/src/diarization/pipeline.rs:250-289`.

### WS3.3 — P1: 25 speakers despite a 5-person participants list (note 9)

**Problem:** The roster is ignored: 5 participants in, 25 speakers out.

**Root cause (confirmed, two-layer):** Sizing is roster-first *only if* the roster maps to
**remote person ids**: `resolve_meeting_speaker_count` (`pipeline.rs:673-751`) uses
`remote_person_ids`; when that's empty (participants added but not linked as remote
`person_id`s — the common case for hand-added names) it falls through to calendar → **Auto,
uncapped** (`DEFAULT_AUTO_THRESHOLD = 0.8`, `sherpa.rs:161`). Even when `AtMost(n)` is set,
`merge_clusters_to_at_most` stops merging below `MERGE_FLOOR = 0.30` cosine similarity
(`sherpa.rs:170-188,772-782`) — a deliberate soft cap. The only warning is at >30 clusters
(`sherpa.rs:168,463-474`).

**Approach:** Use the meeting's **full participant count** (however the participants were
added) as the `AtMost` bound, not just linked remote persons; keep the manual settings
override as `Fixed(n)`. Revisit the soft-cap semantics: with a trusted roster bound, either
lower the merge floor / iterate merges until ≤ n, or keep >n clusters internally but label
the overflow as "Unknown speaker" rather than presenting 25 first-class speakers. Log when
the cap is not honored so we can tune on real meetings.

**Files:** `frontend/src-tauri/src/diarization/pipeline.rs:673-751`,
`frontend/src-tauri/src/diarization/sherpa.rs:161-188,772-782`,
`frontend/src-tauri/src/database/repositories/meeting_participant.rs` (`remote_person_ids`).

### WS3.4 — P2: preserve "you"/channel attribution; stop paying for live labels we discard (note 11)

**Problem:** The final transcript throws away all real-time attributions, including "you" —
even though the user's voice is captured on its own track. If live speaker detection is
discarded anyway, stop spending CPU on it; distinguish "you" vs "others" cheaply and do full
speaker ID at the end.

**Root cause (confirmed):** Live diarization labels are **UI-only** — emitted as
`live-diarization-update` events (`recording_commands.rs:104,164-190`), never written to
`transcripts.speaker`; segments are inserted with `speaker: None` (`worker.rs:270`). The
offline pass then wipes and rebuilds every label from **`system.wav` only**
(`pipeline.rs:435,466-476`), inferring "you" merely as "overlapped no system turn"
(`align.rs:140-144`). Meanwhile the pieces for doing this right already exist: **both
per-track WAVs are saved** (`channel_writer.rs:44-46`, `recording_manager.rs:98-99`) and an
unused per-channel alignment path (`align_turns_to_segments` + `Channel::{Microphone,System}`,
`align.rs:30-105`) short-circuits mic segments to `local`. What's missing is any per-segment
channel tag (schema at `transcript.rs:20`) — the mixed stream destroys channel identity
before STT (`align.rs:109`).

**Approach (phased):**
1. **Tag segments with their dominant channel at capture time.** The pipeline mixes mic +
   system per window and knows both tracks' energy; record a `channel`
   (`microphone|system|mixed`) column on `transcripts` (migration) set from per-window
   RMS dominance. Cheap, no extra STT.
2. **Make the offline pass channel-aware.** Switch to `align_turns_to_segments`: mic-tagged
   segments keep `You` (never overwritten by system-turn overlap); diarization continues to
   run on `system.wav` only (already true) for everyone else. Where the tag says `mixed`,
   fall back to the current overlap heuristic, cross-checked against `mic.wav` energy.
3. **Turn the live diarizer off by default** (settings-gated, existing `live_diarizer`
   Option threading `recording_commands.rs:100-116`) — its labels are discarded today, so
   this is pure CPU savings; the live transcript instead shows the cheap channel tag
   ("You" / "Others") in real time.

**Files:** new migration (`transcripts.channel`),
`frontend/src-tauri/src/audio/pipeline.rs` (window-dominance tag at the transcription send),
`frontend/src-tauri/src/audio/transcription/worker.rs:270`,
`frontend/src-tauri/src/database/repositories/transcript.rs:20`,

## WS4 — Live recording surfaces (P1/P2)

### WS4.1 — P1: transcript jumps to bottom on every new entry (note 2)

**Problem:** Still can't scan the transcript during recording; every append yanks the view
to the bottom. Wanted: stable scrolling unless already at the bottom.

**Root cause (confirmed — two competing auto-scroll systems on nested containers):** The
record screen nests **two** `overflow-y-auto` containers: the outer
`transcriptContainerRef` div (`_components/TranscriptPanel.tsx:66`) and
`VirtualizedTranscriptView`'s inner `scrollRef` div (`VirtualizedTranscriptView.tsx:335`).
The inner one never actually overflows (its parent is height-auto), so the **outer** div is
what visibly scrolls — and it is driven by a legacy scroller in
`TranscriptContext.tsx:72-108` that force-scrolls `scrollHeight` (smooth) on every
`transcripts` change, gated by an unreliable 10px `isUserAtBottomRef`. The 0019 WS1.2
hysteresis fix (`useAutoScroll.ts` + `lib/auto-scroll.ts`, correct "near bottom" logic) went
into the *inner* container's hook — which is watching a div that doesn't scroll. That's why
the fix "didn't take."

**Approach:** One scroll owner. Remove the `TranscriptContext` scroller (and its scroll
listener), collapse the nesting so the container `useAutoScroll` watches is the one that
scrolls (bound the inner div / drop the outer `overflow-y-auto`), and let the existing
`nextAutoFollow` hysteresis govern. Keep `disableAutoScroll` behavior on meeting-details
(already correct).

### WS4.2 — P1: spectrometer shows nothing (note 1)

**Problem:** The vocal-range spectrometer (0025) no longer moves at all.

**Root cause (confirmed structurally; runtime trigger ranked):** The emit code, hook, and
all three render surfaces are **intact and unchanged** by 0028 (verified by diff). But the
`recording-spectrum` emit lives in the **transcription dispatcher**
(`worker.rs:405-409`), whose receiver is fed only **VAD speech segments** ≥800 samples
(`pipeline.rs:982-1017`) — the "sees every mixed chunk" comment at `worker.rs:382-386` is
false. So the bars were always VAD-gated, and anything that starves capture→VAD→dispatcher
freezes them at the render floor, reading as dead. 0028 added likely starvation triggers:
**(H1)** the VAD path now builds a fresh `SincFixedIn` resampler **per call**
(`vad.rs:162` → `audio_processing.rs:645-651`, BlackmanHarris2) on the pipeline task — if it
can't keep up, the new bounded drop-newest capture queue (`pipeline.rs:1126,1176`) sheds
windows; **(H2)** the bounded pipeline→transcription queue (512, drop-newest,
`recording_manager.rs:22,89-90`) drops segments under backpressure; **(H3)** the core_audio
RT-callback `AtomicWaker` rework could stall delivery (would also break transcription —
check whether live transcription still worked when the bars were dead).

**Approach:** Fix the structure, not just the trigger: emit `recording-spectrum` (and
`recording-level`) from the **raw mixed-window path** (`pipeline.rs:1029-1039`, the STEP-4
branch that sees every window), keeping the 80 ms throttle — bars then animate continuously
and survive VAD gating and queue drops. Independently, hoist the `SincFixedIn` construction
out of the per-call `resample` (build-once, reuse) — that's a hot-path allocation fix worth
making regardless, and it also protects transcription latency. Correct the stale comment at
`worker.rs:382-386`.

**Files:** `frontend/src-tauri/src/audio/transcription/worker.rs:382-411`,

## WS5 — Notes integrity (P0/P2)

### WS5.1 — P0: notes edited on one meeting leak into the actively-recording meeting (note 15b)

**Problem:** Notes pasted into a *previous* meeting while a new recording ran also showed up
in the recording meeting.

**Root cause (confirmed):** The record screen renders `<NotepadPanel />` with **no
`meetingId` prop** (`record/page.tsx:418`), so it resolves its target from the sidebar's
`currentMeeting?.id` (`NotepadPanel.tsx:72`) — a **viewed-meeting** tracker that gets
overwritten when any meeting's details are opened (`meeting-details/page.tsx:170`) and is
deliberately **not** reset while a recording is live (`SidebarProvider.tsx:155-159`). So:
record Y → view old meeting X (sets `currentMeeting = X`, paste saves to X — correct) →
return to `/record` (reset skipped) → the live notepad resolves to **X**, loads X's notes
into the recording screen, and autosaves further edits under X. Compounding it, the
debounced save re-resolves the id at fire time (`NotepadPanel.tsx:206-209`) and the 0028
unmount flush fires at whatever id is "current" then (`:189-197`) — both can retarget
mid-flight.

**Approach:** Pin the record-screen notepad to the recording:
`<NotepadPanel meetingId={activeRecordingMeetingId} />`. In `NotepadPanel`, make every
save (debounce + unmount flush) target the id the current content was **loaded for**
(`loadedMeetingIdRef`), never a re-resolved global; flush pending edits before switching
targets on any `Y → X` id change (the current guard only covers `null → id`,
`NotepadPanel.tsx:121`). Add a regression test for the view-another-meeting-while-recording
sequence.

**Files:** `frontend/src/app/record/page.tsx:418`,
`frontend/src/app/_components/NotepadPanel.tsx:72,112-209`.

### WS5.2 — P2: paste into My Notes keeps foreign fonts/styling (note 15a)

**Problem:** Pasted text renders in Times; styling should be discarded to ours.

**Root cause (confirmed, three gaps):** My Notes is a plain `contentEditable`
(`NoteEditor/NoteEditor.tsx` — not the legacy `BlockNoteEditor/` dir). (1) **No `onPaste`
handler** (`NoteEditor.tsx:105-116`) — the browser inserts the clipboard's full HTML,
inline `font-family` and all. (2) `sanitizeNotesHtml` (`notes-html.ts:144-158`) strips
scripts/handlers but **keeps `style`/`class`/`face`/`color`/`size`** — and only runs on
load, not paste. (3) No CSS `font-family` rule on `.note-editor` body text
(`globals.css:174-212`), so pasted inline fonts win unopposed.

**Approach:** Intercept paste and insert sanitized content (allowed tags: the toolbar's
b/i/h1-h3/ul/li/p/br/a; strip all attributes except `href`); extend `sanitizeNotesHtml` to
drop styling attributes (also cleans up already-polluted stored notes on load); add a
`.note-editor` font-family/size rule as the final backstop.

**Files:** `frontend/src/components/NoteEditor/NoteEditor.tsx:105-116`,
`frontend/src/lib/notes-html.ts:144-158`, `frontend/src/app/globals.css:174-212`.
